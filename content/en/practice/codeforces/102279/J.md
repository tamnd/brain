## Solution
## Problem Understanding

The displayed value is a decimal string (X). The glitch affected exactly two digit positions, which means the intended number can be obtained by swapping the digits at two distinct positions of (X). Among all numbers obtainable by one such swap, we need the largest one that is strictly smaller than (X). If no swap produces a smaller valid decimal number, the answer is `-1`.

The input can be as large as (10^{100}), so the number can contain up to 101 digits. This rules out treating the value as a fixed-width machine integer in languages with limited integer types, but it also means the number of digits is tiny. Even an algorithm doing a few million operations on the string is easily fast enough for the one second limit. We can safely use direct enumeration over pairs of positions.

There are three edge cases that a careless implementation can mishandle. For `100`, swapping the `1` with either zero produces a number beginning with zero, so there is no valid smaller positive integer representation and the answer is `-1`. A solution that compares the strings before checking the leading digit could accidentally accept `010` or `001`.

For `999`, every pair contains equal digits. Swapping any pair leaves the number unchanged, so there is no strictly smaller candidate and the answer is `-1`. A solution that accepts a candidate merely because it was generated by a swap would incorrectly return `999`.

For `354`, swapping the first and third digits gives `453`, which is larger, while swapping the second and third digits gives `345`, which is smaller. The correct answer is `345`. This catches implementations that choose the first smaller candidate rather than the greatest one.

## Approaches

The direct approach is to try every pair of digit positions. For each pair, copy the original string, swap those two digits, reject the result if it starts with zero, and compare it with (X). If it is smaller than (X), keep it whenever it is larger than the best candidate found so far.

This brute force is correct because every possible result of changing exactly two digit positions corresponds to one pair (i<j), and the algorithm examines every such pair. Keeping the largest valid candidate then gives exactly the required answer.

The cost of this method is still very small under the actual constraint. With (n) digits there are (\binom n2) possible swaps, and constructing or comparing a candidate can take (O(n)) character operations. Thus the worst-case complexity is (O(n^3)). At the maximum possible length (n=101), there are only (\binom{101}{2}=5050) swaps, giving roughly (5050\cdot101), or about 510,000 character operations.

We can make a small observation that reduces unnecessary work. Suppose (i<j). If (X[i]\le X[j]), swapping them cannot make the number smaller. The first changed position is (i), and its digit either stays equal or becomes larger. A smaller result is possible only when (X[i]>X[j]). We can skip all other pairs.

The brute-force method works because the input contains only about one hundred digits. The observation that only pairs with (X[i]>X[j]) can decrease the number reduces the number of candidates further, but the main reason the simple enumeration is accepted is the unusually small digit count.

| Approach | Time Complexity | Space Complexity | Verdict |
| --- | --- | --- | --- |
| Brute Force | (O(n^3)) | (O(n)) | Accepted |
| Pair filtering with (X[i]>X[j]) | (O(n^3)) worst case | (O(n)) | Accepted |

## Algorithm Walkthrough

1. Read (X) as a string rather than converting it to an integer. The string representation directly gives access to every digit, and it avoids any dependency on integer size.
2. Initialize the best answer as nonexistent. We only create an answer after finding a swap that produces a valid number smaller than (X).
3. Enumerate every pair of positions (i<j). These pairs represent every possible choice of the two digits affected by the glitch.
4. If (X[i]\le X[j]), skip the pair. The first position at which the swapped number differs from (X) is (i), and the new digit there would be (X[j]). Since (X[j]\ge X[i]), the result cannot be strictly smaller.
5. Copy (X) and swap positions (i) and (j). We copy instead of modifying the original string because every candidate must be generated from the same original number.
6. Reject the candidate if its first digit is `0`. A leading zero would no longer represent a valid decimal representation of the intended number.
7. Since (X[i]>X[j]), the candidate is already guaranteed to be smaller than (X), so compare it with the current best candidate. Replace the best candidate when the new one is larger.
8. After all pairs have been examined, print the best candidate if one exists. Otherwise print `-1`.

### Why it works

Consider any valid answer (Y). Since exactly two digits are changed by swapping, there is a unique pair of positions (i<j) whose digits produce (Y). For (Y<X), the first changed position (i) must receive a smaller digit, so necessarily (X[i]>X[j]). The algorithm examines this pair, constructs (Y), and accepts it unless it has an invalid leading zero. Thus every valid candidate is considered. The algorithm keeps the maximum among all accepted candidates, so the final result is exactly the greatest number smaller than (X) obtainable by one swap.

## Python Solution

```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()
    n = len(s)

    best = None

    for i in range(n):
        for j in range(i + 1, n):
            if s[i] <= s[j]:
                continue

            t = list(s)
            t[i], t[j] = t[j], t[i]

            if t[0] == '0':
                continue

            candidate = ''.join(t)

            if best is None or candidate > best:
                best = candidate

    print(best if best is not None else "-1")

if __name__ == "__main__":
    solve()
```

The input is stored in `s` as a string, so each digit can be accessed directly and comparisons between equal-length decimal strings have the same ordering as comparisons between their numerical values.

The nested loops generate every pair (i<j). The condition `s[i] <= s[j]` is a useful pruning step. When the digits are equal, the swap changes nothing. When `s[i] < s[j]`, the first changed digit becomes larger, so the resulting number is larger than (X).

The candidate is created from a fresh list so that a swap cannot affect later iterations. This is a common source of bugs in permutation-style brute force: modifying the original array without restoring it would make later candidates depend on previous swaps.

The leading-zero check happens before accepting the candidate. For example, swapping the `1` and `0` in `100` creates `001`, which must not be treated as the valid number `1`.

There is no integer conversion anywhere in the solution. Python itself supports arbitrary-size integers, but treating the input as a string makes the intended representation explicit and keeps every operation proportional to the number of digits.

## Worked Examples

The first example is `354`.

| (i) | (j) | Original digits | Candidate | Action | Best |
| --- | --- | --- | --- | --- | --- |
| 0 | 1 | `3,5` | skipped | `3 < 5`, so candidate would be larger | none |
| 0 | 2 | `3,4` | skipped | `3 < 4`, so candidate would be larger | none |
| 1 | 2 | `5,4` | `345` | valid and smaller | `345` |

The final answer is `345`. The trace demonstrates why only pairs where the earlier digit is larger need to be considered. Among all possible swaps, only the last pair can decrease the number.

The second example is `100`.

| (i) | (j) | Original digits | Candidate | Action | Best |
| --- | --- | --- | --- | --- | --- |
| 0 | 1 | `1,0` | `010` | reject leading zero | none |
| 0 | 2 | `1,0` | `001` | reject leading zero | none |
| 1 | 2 | `0,0` | skipped | equal digits cannot decrease the number | none |

No valid candidate remains, so the output is `-1`. This trace exercises the leading-zero boundary and also shows why merely finding a lexicographically smaller string is not sufficient.

## Edge Cases

For `100`, the algorithm examines `(0,1)` and `(0,2)`. Both swaps would decrease the number numerically, but they create `010` and `001`, so the leading-zero check rejects both. The pair `(1,2)` contains equal digits and is skipped. The best answer remains nonexistent, so the algorithm prints `-1`.

For `999`, every pair has equal digits. Each pair is skipped by the `s[i] <= s[j]` condition, because swapping equal digits cannot produce a smaller number. The result is `-1`, rather than the unchanged value `999`.

For `2`, there is only one digit, so the nested loops contain no pair at all. No two distinct digits can be swapped, leaving no candidate and producing `-1`.

For `354`, the only useful pair is positions 1 and 2, using zero-based indexing. Since `5 > 4`, swapping them produces `345`. The candidate is valid, smaller than the original, and becomes the best answer. The algorithm prints `345`.

For `11101`, swapping the `1` at position 2 with the `0` at position 3 gives `11011`. The other useful swaps either produce a smaller candidate or do not improve this one. The algorithm keeps `11011`, which is the greatest valid result.

For the maximum-length input, the algorithm never converts the number to a machine integer. Every operation works directly on its decimal characters, so the 101-digit boundary is handled in exactly the same way as a short input.
