## Solution
## Problem Understanding

У каждого эксперимента есть одно число (t_i). Если эксперимент (i) проводится сразу перед экспериментом (j), лаборатория должна перейти от одного оборудования к другому за

[
\max(t_i,t_j)
]

минут. Подготовка оборудования для первого эксперимента и уборка после последнего в суммарное время не входят.

Значит, если эксперименты идут в порядке (p_1,p_2,\ldots,p_n), нужно минимизировать

[
\sum_{k=1}^{n-1}\max(t_{p_k},t_{p_{k+1}}).
]

Нужно вывести не само минимальное время, а перестановку номеров экспериментов, которая его достигает.

При (n\le 3\cdot10^5) перебор перестановок невозможен. Даже алгоритмы (O(n^2)) уже слишком медленные для ограничения в одну секунду, поскольку они потребуют порядка (9\cdot10^{10}) операций в худшем случае. Нам нужен алгоритм порядка (O(n\log n)) или лучше.

Значения (t_i) могут достигать (10^9), поэтому решение не должно зависеть от величины самих чисел. В Python обычные целые числа переполнения не вызывают, хотя само значение суммарного времени могло бы быть порядка (3\cdot10^{14}), если бы его требовалось вычислять.

Первый крайний случай возникает при (n=1). Например, для входа

```
1
1000000000
```

ответом должно быть

```
1
```

Здесь вообще нет пары соседних экспериментов, поэтому нельзя пытаться обращаться к элементам после первого.

Другой важный случай связан с одинаковыми значениями. Для

```
4
7 7 7 7
```

любая перестановка оптимальна, потому что каждая граница стоит ровно (7). Канонический ответ нашего алгоритма будет

```
1 2 3 4
```

Нельзя требовать единственную конкретную перестановку, когда несколько вариантов имеют одинаковую стоимость.

Наконец, нельзя сортировать только сами значения и забывать исходные номера. Например,

```
3
5 1 5
```

порядок значений (1,5,5) действительно оптимален, но выводить нужно номера экспериментов. Корректный канонический ответ здесь

```
2 1 3
```

Если вывести `1 5 5`, это вообще не перестановка номеров экспериментов.

## Approaches

Самый прямой способ состоит в переборе всех (n!) перестановок. Для каждой перестановки можно пройти по ее (n-1) соседним парам и вычислить сумму максимумов. Такой перебор корректен, потому что среди всех рассмотренных перестановок обязательно находится оптимальная. Но его трудоемкость равна (O(n!,n)), то есть уже при (n=10) требуется порядка (10!\cdot9=32,659,200) проверок соседних пар. При (n=3\cdot10^5) такой подход не имеет практического смысла.

Можно попробовать строить порядок жадно, но сначала нужно понять, за что именно мы платим. Рассмотрим любую границу между двумя соседними экспериментами. Ее стоимость равна большему из двух (t), поэтому каждую границу можно мысленно "приписать" тому эксперименту, у которого это большее значение.

Возьмем все эксперименты и расположим их по возрастанию:

[
t_{p_1}\le t_{p_2}\le\ldots\le t_{p_n}.
]

В таком порядке стоимость границы между (p_k) и (p_{k+1}) равна просто (t_{p_{k+1}}). Поэтому общая стоимость равна

[
t_{p_2}+t_{p_3}+\ldots+t_{p_n}.
]

Теперь появляется нижняя граница для любого возможного порядка. Рассмотрим эксперимент с самым маленьким (t). Он может быть единственным экспериментом, который не является большим концом ни одной границы. Каждый другой эксперимент должен хотя бы один раз быть большим концом некоторой соседней пары. Иначе обе его соседние границы, если они существуют, были бы определены значениями других экспериментов, а сам этот эксперимент оказался бы полностью "неоплаченным".

Значит, стоимость любой перестановки не меньше суммы всех (t_i), кроме одного минимального значения. То есть

[
\text{cost}\ge \sum t_i-\min t_i.
]

Именно такую стоимость дает сортировка по возрастанию. Следовательно, она оптимальна.

Получается особенно простой результат: нужно только отсортировать эксперименты по (t_i) и вывести их исходные номера. Если значения равны, порядок между ними не имеет значения.

| Approach | Time Complexity | Space Complexity | Verdict |
| --- | --- | --- | --- |
| Brute Force | (O(n!,n)) | (O(n)) | Too slow |
| Optimal | (O(n\log n)) | (O(n)) | Accepted |

## Algorithm Walkthrough

1. Сохраняем для каждого эксперимента пару `(t_i, i)`, где `t_i` является временем оборудования, а `i` является его исходным номером. Номер нужен, потому что в ответе требуется вывести именно перестановку экспериментов.
2. Сортируем эти пары по `t_i` в неубывающем порядке. Если несколько значений одинаковы, их взаимный порядок не влияет на стоимость, поэтому любой порядок среди них допустим.
3. После сортировки берем номера экспериментов в получившемся порядке. Это и есть требуемая перестановка.
4. Если (n=1), сортировка содержит один элемент, поэтому алгоритм автоматически выводит единственный номер и не требует отдельной обработки.

### Why it works

Пусть эксперименты после сортировки имеют значения

[
a_1\le a_2\le\ldots\le a_n.
]

В отсортированном порядке стоимость всех границ равна

[
a_2+a_3+\ldots+a_n,
]

поскольку на каждой границе справа стоит большее или равное значение.

Теперь рассмотрим произвольную перестановку. Для каждой границы ((u,v)) ее стоимость (\max(t_u,t_v)) можно приписать вершине с большим значением. В линейной цепочке каждый эксперимент, кроме максимум одного, обязан быть большим концом хотя бы одной границы. Следовательно, в сумму обязательно попадут все значения, кроме одного. Чтобы сумма была минимальной, неучтенным нужно оставить самое маленькое значение. Получаем нижнюю границу

[
a_2+a_3+\ldots+a_n.
]

Отсортированный порядок достигает этой границы, значит он оптимален.

## Python Solution

```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    experiments = list(map(int, input().split()))

    order = sorted(range(n), key=lambda i: experiments[i])

    print(*[i + 1 for i in order])

if __name__ == "__main__":
    solve()
```

Сначала считываются все значения `t_i`. Массив `order` содержит индексы от `0` до `n-1`, отсортированные по соответствующим значениям `experiments[i]`. Такой вариант удобнее, чем сортировать сами значения, потому что исходные номера сохраняются автоматически.

Выражение `i + 1` переводит внутреннюю индексацию Python из диапазона `0..n-1` в требуемую условием нумерацию `1..n`.

В сортировке нет необходимости явно задавать второй ключ. При равных `t_i` любой порядок оптимален, а Python сохраняет относительный порядок равных элементов, так что для одинаковых значений получится естественный порядок исходных индексов.

Алгоритм не вычисляет суммарное время, поскольку задача просит только сам оптимальный порядок. Это дополнительно экономит время и исключает ненужные вычисления.

## Worked Examples

Рассмотрим предоставленный пример:

```
5
1 4 5 4 2
```

После сортировки экспериментов по времени получаем порядок номеров (1,5,2,4,3).

| Step | Sorted experiment | (t_i) | Current order |
| --- | --- | --- | --- |
| 1 | 1 | 1 | 1 |
| 2 | 5 | 2 | 1, 5 |
| 3 | 2 | 4 | 1, 5, 2 |
| 4 | 4 | 4 | 1, 5, 2, 4 |
| 5 | 3 | 5 | 1, 5, 2, 4, 3 |

Получаем

```
1 5 2 4 3
```

По формуле из условия стоимость этого порядка равна

[
\max(1,2)+\max(2,4)+\max(4,4)+\max(4,5)
=2+4+4+5=15.
]

В опубликованном примере указано значение 14, но оно не соответствует приведенной в условии формуле (\max(t_i,t_j)). Сам вывод `1 5 2 4 3` совпадает с сортировкой и является оптимальным при формуле из условия.

Теперь рассмотрим второй пример:

```
4
10 1 7 3
```

| Step | Sorted experiment | (t_i) | Current order |
| --- | --- | --- | --- |
| 1 | 2 | 1 | 2 |
| 2 | 4 | 3 | 2, 4 |
| 3 | 3 | 7 | 2, 4, 3 |
| 4 | 1 | 10 | 2, 4, 3, 1 |

Ответ:

```
2 4 3 1
```

Его стоимость равна

[
\max(1,3)+\max(3,7)+\max(7,10)=3+7+10=20.
]

Сумма всех значений без минимального равна (3+7+10=20), поэтому этот порядок достигает доказанной нижней границы.

## Complexity Analysis

| Measure | Complexity | Explanation |
| --- | --- | --- |
| Time | (O(n\log n)) | Сортировка (n) индексов |
| Space | (O(n)) | Массив индексов и исходные значения |

При (n\le3\cdot10^5) сортировка выполняет порядка (n\log n) сравнений, что соответствует стандартной эффективной сложности для такого размера входа. Хранение двух массивов размера (n) также легко укладывается в ограничение памяти 256 МБ.

## Test Cases

Для проверки удобнее сравнивать не только конкретную перестановку, но и ее стоимость, поскольку при одинаковых значениях оптимальных ответов может быть несколько. При этом для предоставленного примера можно проверить и точный ожидаемый вывод, поскольку наша стабильная сортировка дает именно опубликованный порядок.

```python
import sys
import io

def solution(inp: str) -> str:
    data = list(map(int, inp.split()))
    n = data[0]
    t = data[1:1 + n]

    order = sorted(range(n), key=lambda i: t[i])
    return " ".join(str(i + 1) for i in order)

def cost(t, order):
    if len(order) <= 1:
        return 0

    return sum(
        max(t[order[i]], t[order[i + 1]])
        for i in range(len(order) - 1)
    )

# Provided sample
assert solution("5\n1 4 5 4 2\n") == "1 5 2 4 3", "sample"

# Minimum-size input
assert solution("1\n1000000000\n") == "1", "single experiment"

# All values are equal
assert solution("4\n7 7 7 7\n") == "1 2 3 4", "equal values"

# Strictly decreasing input
assert solution("5\n9 8 7 6 5\n") == "5 4 3 2 1", "reverse sorted input"

# Boundary values
assert solution("5\n1000000000 1 999999999 2 1000000000\n") == \
       "2 4 3 1 5", "large values and duplicates"

# Maximum-size input, all values equal
n = 300000
inp = str(n) + "\n" + ("1 " * n).strip() + "\n"
answer = solution(inp)
assert answer == " ".join(map(str, range(1, n + 1))), "maximum n"
```

| Test input | Expected output | What it validates |
| --- | --- | --- |
| `1 / 1000000000` | `1` | Минимальный размер и отсутствие соседних пар |
| `4 / 7 7 7 7` | `1 2 3 4` | Одинаковые значения и несколько оптимальных ответов |
| `5 / 9 8 7 6 5` | `5 4 3 2 1` | Необходимость сортировки по значениям, а не по исходным позициям |
| `5 / 1000000000 1 999999999 2 1000000000` | `2 4 3 1 5` | Большие значения, повторяющийся максимум и корректная индексация |
| `300000 / 1 1 ... 1` | `1 2 ... 300000` | Верхняя граница (n) и линейное хранение ответа |

## Edge Cases

Для (n=1) вход

```
1
1000000000
```

содержит только один эксперимент. После сортировки список индексов остается `[0]`, поэтому после перехода к нумерации с единицы получается `1`. Здесь нет ни одной границы, стоимость равна нулю, и алгоритм не пытается обращаться к несуществующему соседу.

Для одинаковых значений рассмотрим

```
4
7 7 7 7
```

Сортировка сохраняет индексы `1,2,3,4`. Каждая из трех границ имеет стоимость (7), поэтому общая стоимость равна (21). Любая другая перестановка дала бы ту же сумму. Это показывает, почему при равных `t_i` не нужно придумывать специальное правило.

Для уже отсортированного по убыванию массива

```
5
9 8 7 6 5
```

алгоритм меняет его порядок на

```
5 4 3 2 1
```

Значения идут как (5,6,7,8,9), а стоимость равна (6+7+8+9=30). Любой другой порядок не может быть дешевле, поскольку сумма всех значений без минимального равна той же нижней границе.

Для больших значений и повторов рассмотрим

```
5
1000000000 1 999999999 2 1000000000
```

Сортировка дает значения

[
1,2,999999999,1000000000,1000000000
]

и номера

```
2 4 3 1 5
```

Две последние позиции имеют одинаковое значение (10^9), поэтому их можно было поменять местами без изменения ответа. В выбранном порядке каждая граница оплачивается своим большим концом, и достигается нижняя граница

[
2+999999999+1000000000+1000000000.
]

Главная ошибка, которую этот случай выявляет, состоит в сортировке самих `t_i` без сохранения номеров. Ответ должен содержать `2 4 3 1 5`, а не последовательность времен.

Для максимального размера (n=300000) сортировка остается единственной существенной операцией. При одинаковых значениях все индексы сохраняют естественный порядок, а память используется линейно. Это как раз тот случай, ради которого нельзя применять (O(n^2)) построение или перебор перестановок.
