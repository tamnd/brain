## Solution
## Problem Understanding

We have a star at a given point in three-dimensional space. Each planet is also given by its three coordinates and a name. The task is to print the planet names from the one closest to the star to the one farthest away.

For a planet at `(x, y, z)` and a star at `(sx, sy, sz)`, its Euclidean distance is

`sqrt((x - sx)^2 + (y - sy)^2 + (z - sz)^2)`.

The square root is unnecessary for comparing two distances. Since the square-root function is strictly increasing for nonnegative values, comparing the distances is exactly the same as comparing their squared distances. This lets us use integer arithmetic throughout the algorithm.

The official problem gives a 1 second time limit and 256 MB of memory. It does not publish a numeric upper bound for `n` on the problem page, only that `n` is a positive integer. That makes an `O(n log n)` solution the natural target: it remains practical for very large inputs, while an `O(n^2)` method would quickly become unusable. The input itself contains only a constant amount of work per planet, so storing all planets and their sorting keys requires linear memory.

The first edge case is a planet whose coordinates equal the star's coordinates. For example,

```
0 0 0
1
0 0 0 Home
```

has output

```
Home
```

Its squared distance is zero. A careless implementation that initializes the smallest distance to a positive sentinel but otherwise handles subtraction correctly will still work, while an implementation that assumes every planet has a strictly positive distance can mishandle this case.

A second edge case is a planet lying in the negative direction of one or more axes. For example,

```
10 10 10
2
9 10 10 A
8 10 10 B
```

has output

```
A
B
```

because the distances are `1` and `2`. The subtraction must be performed before squaring. Comparing coordinates directly, or accidentally using `x - sx` without taking the square, would not represent geometric distance.

A third common mistake is taking the square root before sorting. For example,

```
0 0 0
2
3 4 0 A
0 0 6 B
```

has output

```
A
B
```

because the squared distances are `25` and `36`. Computing the actual distances works mathematically, but it introduces floating-point arithmetic without providing any benefit. Squared distances give exact integer comparisons.

The input guarantees that no two planets have the same distance from the star, so there is no need to define a tie-breaking rule.

## Approaches

The most direct brute-force approach is to repeatedly search for the closest planet that has not yet been printed. On the first iteration we inspect all `n` planets, on the second we inspect `n - 1`, and so on. The total number of distance comparisons is

`n + (n - 1) + ... + 1 = n(n + 1) / 2`.

Thus the method takes `O(n^2)` time. It is correct because every iteration explicitly chooses the remaining planet with minimum distance, but its quadratic growth makes it unsuitable when `n` becomes large. For `n = 100000`, it performs about `5 * 10^9` comparisons, far beyond what a 1 second time limit can accommodate.

The key observation is that the problem is simply asking us to order planets by one numeric key, their distance from the star. Once each planet has a squared distance attached to it, the geometric part is finished. We can put every pair `(squared_distance, name)` into an array and sort that array by the first component.

The brute-force method works because it discovers the minimum one planet at a time, but it repeatedly scans planets whose relative order has already been determined. The observation that all planets can be assigned their distance independently lets us compute every key once and delegate the ordering to a standard `O(n log n)` sort.

There is no need to calculate square roots. For two planets with squared distances `d1²` and `d2²`, `d1 < d2` exactly when `d1² < d2²`. Python integers also avoid overflow, so even large coordinate values can be squared safely.

| Approach | Time Complexity | Space Complexity | Verdict |
| --- | --- | --- | --- |
| Brute Force | O(n²) | O(n) | Too slow for large n |
| Optimal | O(n log n) | O(n) | Accepted |

## Algorithm Walkthrough

1. Read the star's coordinates `(sx, sy, sz)`. Every planet's distance will be measured relative to this same point.
2. Read the number of planets and, for each planet, read `(x, y, z)` and its name. Compute

`d2 = (x - sx)^2 + (y - sy)^2 + (z - sz)^2`.

We use the squared distance because it preserves the ordering of ordinary distances while avoiding square roots and floating-point precision.
3. Store `(d2, name)` for every planet in an array. The distance is placed first because that is the value by which the array needs to be ordered.
4. Sort the array. Python's tuple ordering sorts primarily by the first component, so the planets automatically appear from smallest squared distance to largest squared distance.
5. Print the names in the resulting order. Since the input guarantees distinct distances, no tie-handling is necessary.

### Why it works

The invariant is that every stored planet has an exact key equal to its squared Euclidean distance from the star. For any two planets `A` and `B`, the ordering of their keys is the same as the ordering of their actual distances because square root is strictly increasing on nonnegative numbers. Sorting these keys therefore produces exactly the closest-to-farthest ordering required by the problem. No planet can appear in the wrong position because every comparison made by the sort is equivalent to comparing the true geometric distances.

## Python Solution

```python
import sys
input = sys.stdin.readline

def solve():
    sx, sy, sz = map(int, input().split())
    n = int(input())

    planets = []

    for _ in range(n):
        x, y, z, name = input().split()
        x = int(x)
        y = int(y)
        z = int(z)

        dx = x - sx
        dy = y - sy
        dz = z - sz

        dist2 = dx * dx + dy * dy + dz * dz
        planets.append((dist2, name))

    planets.sort()

    sys.stdout.write("\n".join(name for _, name in planets))

if __name__ == "__main__":
    solve()
```

The first two input lines give the star and the number of planets. The loop then converts the three coordinate fields to integers while leaving the planet name as a string.

The subtraction is done coordinate by coordinate before squaring. This is the direct translation of the squared 3D distance formula, and using three separate variables makes it harder to accidentally square the absolute coordinates instead of the coordinate differences.

The tuple `(dist2, name)` is sufficient for sorting. Python compares tuples lexicographically, so `dist2` determines the order. The problem guarantees distinct distances, which means the second tuple component never affects the answer.

The final generator extracts only the names. `"\n".join(...)` produces exactly one name per output line without adding an unnecessary trailing newline. There is no integer-overflow concern in Python because its integers have arbitrary precision.

## Complexity Analysis

| Measure | Complexity | Explanation |
| --- | --- | --- |
| Time | O(n log n) | Computing all distances takes O(n), followed by sorting n planets |
| Space | O(n) | The array stores one distance and one name for every planet |

The published time limit is 1 second and the memory limit is 256 MB. Since the algorithm performs only constant work per planet before one `O(n log n)` sort, it is appropriate for a large `n`. The memory consumption grows linearly because every planet must be retained for sorting.

## Edge Cases

A planet at exactly the star's coordinates has squared distance zero. For

```
0 0 0
1
0 0 0 Home
```

the algorithm computes `dx = dy = dz = 0`, so `dist2 = 0`. Sorting a one-element array leaves `Home` in place, and the output is `Home`. There is no special case in the implementation because zero is naturally the smallest possible squared distance.

Negative coordinates require no separate handling. For

```
10 10 10
2
9 10 10 A
8 10 10 B
```

the algorithm computes squared distances `1` and `4`. Sorting produces `A` before `B`. The negative value of `dx` is harmless because it is squared, which is exactly what the Euclidean distance formula requires.

The implementation also avoids floating-point errors. For

```
0 0 0
2
3 4 0 A
0 0 6 B
```

the keys are `25` and `36`. The actual distances are `5` and `6`, but computing square roots would add work and floating-point values without changing the ordering. Integer squared distances give the same result exactly.

Finally, planets may differ along different coordinate axes while having very similar distances. The implementation always computes all three squared differences before comparing planets. For example,

```
0 0 0
2
1 1 1 A
2 0 0 B
```

produces squared distances `3` and `4`, so the output is

```
A
B
```

A solution that compares only one coordinate would fail on this kind of input, while the full squared-distance key correctly incorporates all three dimensions.
