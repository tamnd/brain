## Solution
## Problem Understanding

We are given exactly three integers, representing the three positions of a sequence. The task is to decide whether the sequence is strictly increasing. In other words, the first value must be smaller than the second, and the second must be smaller than the third.

The output is `SORTED` when both comparisons hold. If either comparison fails, including the case where two neighboring values are equal, the output is `UNSORTED`. The official problem has a 1 second time limit and a 256 MB memory limit, with only three integers in the input.

Because the sequence always contains exactly three values, there is no meaningful large-input performance concern. Any constant-time solution is comfortably within the limits, and even a generic sorting-based solution would be fast enough. The more useful algorithmic observation is that sorting is unnecessary: the required condition is stated directly as two strict inequalities.

The main edge case is equality. For example,

```
6 6 7
```

must produce

```
UNSORTED
```

because the first value is not strictly smaller than the second. A careless implementation using `<=` instead of `<` would incorrectly accept this sequence. This is also the official second sample.

Another edge case is a sequence that decreases only at the second comparison. For example,

```
1 5 3
```

must produce

```
UNSORTED
```

Even though `1 < 5` is true, the condition `5 < 3` is false. Checking only the first pair would silently accept an invalid sequence.

The reverse situation is also possible:

```
5 2 8
```

must produce

```
UNSORTED
```

because the first comparison already fails. There is no need to inspect the third value once either required inequality is false.

## Approaches

A straightforward brute-force approach would generate every possible ordering of the three values and look for the increasing arrangement. There are only `3! = 6` permutations, so this would perform a constant number of operations and would be correct if implemented carefully. For this particular problem, however, it solves a much more general problem than necessary. There is no input-size threshold where this brute force becomes too slow, because the number of values is fixed at three. In a generalized version with `n` values, the same strategy would require `n!` permutations, reaching `3,628,800` possibilities already at `n = 10` and becoming unusable quickly.

A more direct approach comes from reading the definition of sorted order literally. The sequence `[a, b, c]` is strictly increasing exactly when `a < b` and `b < c`. We can test those two conditions directly and print the corresponding result. The two approaches are both constant-time for the actual problem, but the direct comparison has no unnecessary work and expresses the required condition exactly.

| Approach | Time Complexity | Space Complexity | Verdict |
| --- | --- | --- | --- |
| Brute Force | O(3!) = O(1) | O(1) | Accepted, but unnecessary |
| Optimal | O(1) | O(1) | Accepted |

## Algorithm Walkthrough

1. Read the three integers `a`, `b`, and `c`. They are the values whose ordering must be checked.
2. Test whether `a < b` and `b < c`. Both comparisons must be true because the problem requires strict increasing order, not non-decreasing order.
3. Print `SORTED` if both comparisons are true. Otherwise print `UNSORTED`. A single failed comparison is enough to reject the sequence.

### Why it works

The algorithm checks exactly the two conditions that define a strictly increasing sequence of length three. If both `a < b` and `b < c` hold, every consecutive pair is in the required order, so the whole sequence is sorted. If either condition fails, at least one consecutive pair violates strict ordering, so the sequence cannot be sorted. Equality is correctly rejected because `<` is used rather than `<=`.

## Python Solution

```python
import sys
input = sys.stdin.readline

def solve():
    a, b, c = map(int, input().split())

    if a < b and b < c:
        print("SORTED")
    else:
        print("UNSORTED")

if __name__ == "__main__":
    solve()
```

The input line is read once and split into the three integer values. Since the problem contains exactly one test case, there is no test-case loop.

The condition uses two comparisons joined by `and`. Python evaluates this as true only when both inequalities hold, matching the mathematical definition of strict increasing order. Using `<=` here would be an off-by-one style logical error because equal neighboring values are not considered sorted by this problem.

No sorting operation is needed, and no additional data structure is required. Python integers also have arbitrary precision, so there is no integer-overflow concern regardless of the magnitude permitted by the input.

## Edge Cases

The equality case `6 6 7` is handled because the first comparison evaluates to `6 < 6`, which is false. The algorithm immediately chooses `UNSORTED`. A non-strict comparison such as `6 <= 6` would produce the wrong result, so the choice of operator is essential.

The case `1 5 3` demonstrates why both adjacent pairs must be checked. The first comparison, `1 < 5`, succeeds, but the second comparison, `5 < 3`, fails. The algorithm combines both conditions with `and`, so it correctly prints `UNSORTED`.

The case `5 2 8` exercises failure at the first comparison. Since `5 < 2` is false, the complete sequence cannot be increasing, regardless of the value of the third element. The algorithm still evaluates the complete Boolean expression correctly and prints `UNSORTED`.

Finally, `1 2 3` demonstrates the only situation that produces `SORTED`: both adjacent comparisons are true. The algorithm does not require the values to have any particular difference, only the strict ordering between consecutive elements.
