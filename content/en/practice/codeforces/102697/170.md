## Problem Understanding

The problem models a cup of coffee that starts at 210 degrees in a room whose ambient temperature is 70 degrees. Its temperature follows Newton's law of cooling,

[
T(t)=T_s+(T_0-T_s)e^{-kt}.
]

Here, (T_s=70), (T_0=210), and the unknown cooling constant (k) is determined by the given calibration point: after 15 minutes, the coffee has cooled to 120 degrees. For every test case, we are given a target temperature (T(t)), and we must output the time in minutes when the coffee reaches that temperature. The official statement gives exactly these quantities and the sample outputs.

The useful input size is very small from an algorithmic perspective. There are only (n) independent temperature queries, and each query requires a constant number of arithmetic and logarithm operations. The time limit is 1 second and the memory limit is 256 MB, so even a linear pass over a large number of test cases is trivial. There is no reason to use numerical simulation or any iterative method when the equation can be inverted directly.

The physically meaningful target temperatures lie between the initial temperature and the ambient temperature. For (T=210), the answer is exactly 0 because the coffee starts there. For a target such as (T=120), the answer is 15 by the calibration condition. A target below 70 would never be reached at a finite time because the model approaches 70 from above. A target equal to 70 is similarly approached only asymptotically. The statement describes each test value only as a positive integer, so these non-physical values are best understood as outside the intended domain of the cooling model.

For example, the input

```
1
210
```

has output 0, because no cooling time is required to reach the starting temperature. A careless implementation that assumes the logarithm argument is always strictly greater than 1 could still compute this correctly, but it may accidentally introduce a special case through an incorrect formula.

For the input

```
1
120
```

the correct output is 15. The calibration point itself must be preserved. A formula that approximates (k) too early with a rounded decimal can produce a slightly different value and lose precision unnecessarily.

For a target close to the room temperature, such as

```
1
71
```

the answer is much larger than the sample values because the exponential curve becomes increasingly slow near 70. An implementation that assumes the cooling time is bounded by a small constant or simulates temperature minute by minute cannot obtain the required real-valued answer accurately.

## Approaches

A brute-force numerical approach could simulate the cooling process at small time increments, repeatedly evaluate (T(t)), and stop when the simulated temperature becomes close enough to the target. This is conceptually straightforward because Newton's formula directly tells us the temperature at any chosen time. The problem is that the answer is a real number, so there is no natural discrete time step that gives the required precision. If we tried a step of (10^{-6}) minutes and needed to cover roughly 72 minutes for temperatures near 71 degrees, one test could require about 72 million evaluations. With (n) test cases, that quickly becomes too slow, and reducing the step further only makes the situation worse.

A more sophisticated numerical brute force would use binary search on time. Since the temperature decreases monotonically, we can find the time corresponding to a target temperature by repeatedly checking the midpoint. About 60 to 100 iterations are enough for double precision, so this approach would actually be fast enough. However, it is solving an equation that has an exact algebraic inverse, making the iterative machinery unnecessary.

The key observation is that the unknown (k) does not need to be estimated numerically. The calibration point gives it exactly in logarithmic form. Substituting (T_s=70), (T_0=210), and (T(15)=120) gives

[
120=70+140e^{-15k},
]

so

[
50=140e^{-15k},
]

and hence

[
e^{-15k}=\frac{5}{14}.
]

Taking natural logarithms,

[
k=\frac{\ln(14/5)}{15}.
]

Now for an arbitrary target temperature (T),

[
T=70+140e^{-kt}.
]

Rearranging,

[
e^{-kt}=\frac{T-70}{140}.
]

Taking logarithms again,

[
-kt=\ln\left(\frac{T-70}{140}\right),
]

so

[
t=\frac{\ln\left(\frac{140}{T-70}\right)}{k}.
]

Substituting the value of (k),

[
\boxed{
t=
15\frac{\ln\left(\frac{140}{T-70}\right)}
{\ln(14/5)}
}.
]

The brute-force approach works because the temperature function is monotonic, but it spends computation searching for a value that algebra can provide directly. The observation that the exponential equation can be inverted reduces every test case to a constant amount of work.

| Approach | Time Complexity | Space Complexity | Verdict |
| --- | --- | --- | --- |
| Brute Force | O(n · P) for P numerical steps | O(1) | Too slow for fine precision |
| Optimal | O(n) | O(1) | Accepted |

## Algorithm Walkthrough

1. Read the number of temperature queries. Each query is independent, so there is no state to maintain between test cases.
2. Read the target temperature (T). The fixed physical constants are already known: the room is at 70 degrees, the coffee starts at 210 degrees, and the calibration point is 120 degrees after 15 minutes.
3. Compute the time directly with

[
t=
15\frac{\ln(140/(T-70))}
{\ln(14/5)}.
]

The numerator comes from inverting the cooling equation for the requested temperature, while the denominator comes from the calibration measurement used to determine the cooling constant.

1. Print the resulting floating-point value. No rounding to a fixed number of decimal places is required because the judge accepts a sufficiently accurate real number.

Why it works: after rearranging Newton's equation, every target temperature corresponds to exactly one finite time because the exponential term decreases continuously from 1 toward 0. The calibration point determines the only unknown parameter (k), and the second logarithm isolates (t). Thus the value printed for each query is precisely the time represented by the given cooling model.

## Python Solution

```python
import sys
import math

input = sys.stdin.readline

def solve():
    n = int(input())

    denominator = math.log(14 / 5)

    for _ in range(n):
        temperature = int(input())

        time = 15 * math.log(140 / (temperature - 70)) / denominator
        print(time)

if __name__ == "__main__":
    solve()
```

The denominator is constant for every test case, so it is computed once rather than repeatedly. It represents the logarithmic form of the calibration measurement.

For each target temperature, `temperature - 70` is the amount by which the coffee is above room temperature. Dividing 140 by this quantity gives the inverse of the exponential factor. Taking its natural logarithm isolates the time-dependent exponent.

The multiplication by 15 and division by `log(14 / 5)` incorporate the known calibration point. Keeping the calculation in floating point avoids introducing rounding errors from manually approximating the cooling constant.

There is no integer overflow issue because Python integers have arbitrary precision, and the main calculation uses Python's double-precision floating-point `float`. The only boundary that matters mathematically is `temperature - 70 > 0`, since the logarithm must receive a positive argument.
