## Solution
## Problem Understanding

The dungeon is an (n \times n) grid. A dot represents a walkable cell, while `X` represents a wall. The player begins at the upper-left cell and may move one cell at a time in the four cardinal directions. The task is to count how many walkable cells belong to the same connected region as the starting cell. Diagonal movement is not allowed, and walls and positions outside the grid cannot be crossed. The official statement gives the time limit as 1 second and the memory limit as 256 MB, but it does not provide a numeric upper bound for (n).

The key consequence of the missing numeric bound is that the algorithm should scale with the number of cells rather than perform repeated work over the grid. The grid itself contains (n^2) characters, so merely reading the input already takes (O(n^2)) time. An (O(n^2)) traversal is consequently the natural target. An (O(n^3)) or (O(n^4)) method would become problematic as (n) grows, especially under the one-second limit.

There are several edge cases where a careless implementation can fail. If the grid is a single walkable cell, such as

```
1
.
```

the answer is `1`. An implementation that only counts cells reached after making a move can incorrectly return `0`.

If the starting cell is surrounded by walls, for example

```
3
.X.
XXX
...
```

the only accessible cell is the starting cell, so the answer is `1`. A traversal must count the starting position before looking for its neighbors.

A region can also touch itself through multiple routes. For example,

```
3
...
...
...
```

has answer `9`. A careless search that does not mark cells as visited can enter the same cycle repeatedly and either count cells multiple times or never terminate.

Finally, walls elsewhere in the dungeon do not affect the answer unless they separate the starting component. For

```
3
..X
XXX
...
```

the answer is `2`, because only the two cells in the upper-left component are reachable. Counting every dot in the grid would incorrectly return `5`.

## Approaches

A direct brute-force approach could repeatedly scan the entire grid to find cells that can be reached from the cells already known to be accessible. For example, after discovering one new cell, we could inspect all (n^2) positions to see whether that cell should cause another position to become reachable. In the worst case there can be (n^2) discoveries, and each discovery may trigger a full (n^2)-cell scan, giving (n^4) grid inspections. For (n=1000), that is up to (10^{12}) inspections, far beyond what a one-second program can handle.

The brute-force method works because reachability is transitive: once a cell is reachable, every adjacent walkable cell becomes reachable as well. The problem is that repeatedly rediscovering this fact by scanning unrelated cells wastes almost all of the computation.

The useful observation is that this is exactly a connected-component problem on a grid. Each walkable cell is a graph vertex, and an edge exists between two vertices when their cells share a side. We only need the connected component containing ((0,0)). A breadth-first search or depth-first search visits every reachable cell once and examines its four possible neighbors. Since each cell is processed once, the total work is proportional to the number of cells in the grid.

A visited marker is essential. Without it, a pair of adjacent walkable cells could keep sending the search back to each other. We can avoid a separate visited array by changing every discovered dot into `X`. Since those cells can never need to be processed again, mutating the grid gives the same effect while using less auxiliary memory.

| Approach | Time Complexity | Space Complexity | Verdict |
| --- | --- | --- | --- |
| Repeated full-grid scanning | (O(n^4)) | (O(n^2)) | Too slow |
| BFS or DFS flood fill | (O(n^2)) | (O(n^2)) | Accepted |

## Algorithm Walkthrough

1. Read the (n \times n) dungeon and check the starting cell. If it is a wall, there is no walkable starting component, so the answer is `0`. The original problem describes the starting position as a space in the dungeon, but handling this case makes the implementation robust.
2. Put the starting cell into a stack and mark it as visited immediately. We use a stack for iterative depth-first search, which avoids Python's recursion-depth limitation.
3. While the stack is not empty, remove one cell and increase the answer by one. A cell is counted when it is removed because every cell placed into the stack has already been confirmed to be a new reachable cell.
4. Examine the four neighboring positions. For each neighbor, first check that its row and column are inside the grid. Then check whether it is a dot. If it is, change it to `X` and push it onto the stack.

Marking the neighbor before pushing it is deliberate. Suppose two already discovered cells both touch the same new cell. The first one marks and pushes it, so the second one will see `X` and cannot push it again.
5. When the stack becomes empty, every cell reachable from the starting position has been visited. Print the number of processed cells.

### Why it works

The invariant is that every cell currently in the stack, and every cell already processed, belongs to the connected component of the starting cell, and every cell is marked as soon as it is discovered. When the algorithm moves from a processed cell to a walkable neighbor, that neighbor is connected to the starting component by the existing path followed by this one additional edge, so adding it is correct. Conversely, any reachable cell must have a path from the start. Following that path one edge at a time, the search eventually discovers every walkable cell on the path unless it was already discovered earlier. Thus the stack eventually contains and processes every reachable cell exactly once, while walls and disconnected regions are never counted.

## Python Solution

```python
import sys
from collections import deque

input = sys.stdin.readline

def solve():
    n = int(input())
    grid = [bytearray(input().strip(), "ascii") for _ in range(n)]

    if grid[0][0] != ord('.'):
        print(0)
        return

    stack = [(0, 0)]
    grid[0][0] = ord('X')
    answer = 0

    directions = ((1, 0), (-1, 0), (0, 1), (0, -1))

    while stack:
        r, c = stack.pop()
        answer += 1

        for dr, dc in directions:
            nr = r + dr
            nc = c + dc

            if 0 <= nr < n and 0 <= nc < n and grid[nr][nc] == ord('.'):
                grid[nr][nc] = ord('X')
                stack.append((nr, nc))

    print(answer)

if __name__ == "__main__":
    solve()
```

The grid is stored as `bytearray` rows so that a discovered cell can be changed directly from `.` to `X`. This removes the need for a second (n \times n) Boolean visited matrix.

The stack contains coordinates waiting to be processed. The starting cell is marked before it enters the stack, rather than when it is popped, because marking at insertion time prevents duplicate entries.

The four direction pairs represent down, up, right, and left. The boundary condition uses `0 <= nr < n` and `0 <= nc < n`, which exactly describes valid grid coordinates and avoids both negative indexing and access beyond the last row or column.

There is no recursion, so even a very large connected component cannot overflow Python's recursion limit. Python integers also have arbitrary precision, although the answer is at most (n^2), so ordinary integer overflow would not be an issue anyway.

The imported `deque` is not actually needed by this implementation because a Python list is sufficient for a stack. Keeping the stack as a list gives efficient (O(1)) `append` and `pop` operations from the end.

## Complexity Analysis

| Measure | Complexity | Explanation |
| --- | --- | --- |
| Time | (O(n^2)) | Each of the (n^2) cells is read once, and every reachable cell examines exactly four directions. |
| Space | (O(n^2)) | The grid occupies (O(n^2)) space, and the DFS stack can contain (O(n^2)) coordinates in the worst case. |

The (O(n^2)) running time is asymptotically optimal because the input itself contains (n^2) cells and must be read. The problem specifies a one-second time limit and 256 MB of memory, so avoiding repeated full-grid scans is the main requirement.

## Edge Cases

For the one-cell dungeon

```
1
.
```

the algorithm marks `(0,0)` before starting the search and places it on the stack. It is popped once, so `answer` becomes `1`. All four candidate neighbors fail the boundary check. The stack becomes empty and the output is `1`.

For an isolated starting cell,

```
3
.X.
XXX
...
```

the algorithm processes `(0,0)` and examines its four neighbors. The right and downward positions are walls, while the other two positions are outside the grid. No new cell is pushed, so the search ends immediately with answer `1`. The lower row is irrelevant because walls disconnect it from the start.

For a completely open grid,

```
3
...
...
...
```

every discovered cell can lead to another undiscovered neighbor. Each cell is marked when it is pushed, so even though many cells have multiple paths between them, no cell enters the stack twice. All nine cells are eventually processed, giving `9`.

For the disconnected case

```
4
..XX
..XX
XXXX
....
```

the first two rows form a component of four cells, while the bottom row forms another component of four cells. Starting from `(0,0)`, the search can reach `(0,1)`, `(1,0)`, and `(1,1)`, but every route toward the bottom row encounters an `X`. The answer is consequently `4`, not `8`.

The large all-dot test exercises the case where the entire grid is one connected component. With a (1000 \times 1000) grid, the algorithm processes exactly one million cells and examines four directions for each. No recursive calls are made, and every cell is marked immediately when discovered, so the traversal remains linear in the input size.
