## Solution
## Problem Understanding

We are given the elevations of points visited during a bike ride, in the order in which they were visited. Consecutive elevations form individual riding segments. A hill is a maximal consecutive stretch where every segment goes strictly upward. Its vertical rise is simply the elevation at the end of that stretch minus the elevation at its beginning.

The task is to find the largest such vertical rise. A downhill segment or a flat segment breaks the current uphill stretch, so the next increasing segment starts a new candidate hill. The statement guarantees that at least one strictly uphill segment exists.

The official problem page does not specify an upper bound for `n` or for the elevation values. It gives a 1 second time limit and 256 MB memory limit. Since the required computation can be done with one pass over the elevations, an `O(n)` algorithm is the natural target and is safe even if `n` is very large. A quadratic algorithm would become problematic as soon as `n` reaches the usual competitive-programming scale of around `10^5`, where roughly `5 * 10^9` pairs would have to be considered.

There are several edge cases that can make an implementation subtly wrong. A flat segment must terminate a hill. For example,

```
8
100 200 300 300 400 500 600 700
```

has answer `400`, not `600`. The first rise from `100` to `300` is one hill, the equal `300` values break it, and the second hill rises from `300` to `700`. A careless implementation that treats non-decreasing sequences as uphill would incorrectly combine the two parts and return `600`. This is also the third official sample.

A downhill segment also terminates the current hill. For example,

```
7
600 650 700 690 740 520 600
```

has answer `100`. The first hill rises from `600` to `700`, giving `100`, while `690` to `740` gives `50` and `520` to `600` gives `80`. An implementation that keeps accumulating after a downhill step could incorrectly combine unrelated climbs.

A hill can end exactly at the final elevation, so the last increasing run must be checked even though there is no following downhill or flat segment. For example,

```
5
100 150 120 300 500
```

has answer `380`, from `120` to `500`. An implementation that only updates the answer when it encounters a break would miss the final hill and might return `50`.

The smallest valid input must contain at least two points because the statement guarantees a positive uphill section. For example,

```
2
10 20
```

has answer `10`. The single available segment itself is a complete hill.

## Approaches

The direct brute-force solution considers every possible starting point and extends the hill while the elevations continue increasing. Whenever the next elevation is not strictly larger, that candidate hill stops. Since the rise of a valid uphill section is determined entirely by its first and last elevation, this approach is correct: every possible hill is examined and its rise can be compared with the current maximum.

The problem is that many of those candidates overlap. On a strictly increasing array of length `n`, starting at the first point causes roughly `n - 1` extensions, starting at the second causes `n - 2`, and so on. The total number of extensions is

`(n - 1) + (n - 2) + ... + 1 = n(n - 1)/2`.

Thus the worst case is `O(n^2)`. For `n = 100000`, this is about `4,999,950,000` extensions, far beyond what a 1 second solution can handle.

The useful observation is that an uphill hill does not require us to remember every intermediate increase. Suppose the current hill started at elevation `start`, and we are currently at elevation `h`. As long as the next elevation is larger, the whole sequence remains one valid hill, and its rise is simply `h - start`. When the next value is not larger, the hill has ended. We can then discard all of its internal points and start the next candidate at the new elevation.

This turns the problem into a single scan. We maintain the starting elevation of the current strictly increasing run and compare each new elevation with the previous one. When the new value is larger, the current hill's rise is `current - start`. When it is not larger, the current run ends and the new point becomes the start of the next possible hill.

The brute-force works because it explicitly explores every increasing run, but fails by repeatedly examining the same prefixes. The observation that an increasing run can be represented only by its starting elevation and current endpoint lets us process each adjacent pair exactly once.

| --- | --- | --- | --- |
| Brute Force | O(n²) | O(n) | Too slow |
| Optimal | O(n) | O(1) auxiliary | Accepted |

## Algorithm Walkthrough

1. Read the number of elevation points and the elevation array. We only need the previous elevation, the starting elevation of the current uphill run, and the best rise found so far.
2. Set `start` to the first elevation and `prev` to the first elevation. At the beginning, the current hill contains no segment, so its rise is zero.
3. Scan the remaining elevations from left to right. For each `cur`, compare it with `prev`.
4. If `cur > prev`, the ride has continued strictly uphill. Keep the same `start`, because every increasing segment since `start` belongs to the same hill. The current rise is `cur - start`, so update the maximum if this value is larger.
5. If `cur <= prev`, the current hill has ended. Equality counts as a break just like a downhill segment because the definition requires every segment to be strictly uphill. Set `start = cur` so that a new hill can begin at this point.
6. Set `prev = cur` and continue scanning. The final value of the maximum is the answer.

### Why it works

The invariant is that immediately before processing each new elevation, `start` is the first elevation of the current maximal strictly increasing suffix of the processed array. If the next elevation is larger than `prev`, that suffix remains strictly increasing, so its rise is exactly `cur - start`. If the next elevation is not larger, no valid uphill section can cross that boundary, so the current suffix must end and the new point is the only possible starting point for a hill that follows it. Since every valid hill is exactly one maximal strictly increasing run, every candidate is evaluated and the largest rise is retained.

## Python Solution

```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))

    start = a[0]
    prev = a[0]
    best = 0

    for cur in a[1:]:
        if cur > prev:
            best = max(best, cur - start)
        else:
            start = cur

        prev = cur

    print(best)

if __name__ == "__main__":
    solve()
```

The first two variables, `start` and `prev`, represent the two endpoints needed to describe the current hill. `start` does not change while the elevations are strictly increasing, because every new point still belongs to the same hill.

The strict comparison `cur > prev` is the central detail. Using `cur >= prev` would incorrectly allow a flat segment to remain inside a hill. The official third sample is specifically useful for detecting this mistake.

When a break occurs, `start` is assigned `cur`, rather than `prev`. This is what allows the next segment to form a hill beginning at the current point. For example, in `100 150 120 300`, the new hill starts at `120`, not at `150`.

The answer is updated immediately whenever an increasing segment is found. This handles a hill that reaches the end of the array, where there is no later value to trigger a reset. No special post-processing is necessary.

Python integers have arbitrary precision, so elevation differences do not risk integer overflow.
