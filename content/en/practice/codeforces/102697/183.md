## Solution
## Problem Understanding

The problem asks us to print the first `n` positive integers that survive after every multiple of `3` is removed. The number `0` is also removed, but since the output contains only positive integers, it never appears in the answer. The surviving sequence begins

`1, 2, 4, 5, 7, 8, 10, 11, ...`

so every block of three consecutive integers contributes exactly two survivors.

The input contains one positive integer `n`, the number of surviving integers that must be printed. The output contains those `n` integers, one per line. The official statement gives a one-second time limit and 256 MB of memory, with no explicit upper bound for `n` shown on the problem page. Since the output itself contains `n` integers, any solution must spend at least `O(n)` time just writing the answer. An algorithm that does more than linear work is unnecessary.

The first subtle case is `n = 1`. The answer is `1`, not `0`, because `0` is explicitly destroyed.

```
1
```

The correct output is:

```
1
```

An implementation that starts its search from `0` and treats every non-multiple of `3` as a survivor could accidentally print `0` if it forgets that the output concerns positive integers.

Another boundary case occurs exactly at the end of a complete block. For example:

```
3
```

The correct output is:

```
1
2
4
```

The third survivor is `4`, not `3`. A careless formula such as `2 * n` or an incorrect grouping of the numbers can easily include a multiple of `3`.

A larger example also shows why the gap between consecutive answers is not constant:

```
5
```

The correct output is:

```
1
2
4
5
7
```

The gaps alternate between `1` and `2`. Trying to generate the answer using a constant increment therefore fails.

## Approaches

The most direct solution is to simulate the destruction process. Start at `1`, test each integer, and print it whenever it is not divisible by `3`. Stop after printing `n` survivors. This is correct because the test `x % 3 != 0` is exactly the definition of an integer that remains alive.

The simulation does not actually become asymptotically too slow here. Among every three consecutive positive integers, exactly two survive, so finding the first `n` survivors requires examining exactly

`n + floor((n - 1) / 2)`

positive integers. That is at most about `1.5n` modulo operations, followed by `n` output operations. Thus the brute-force method is already `O(n)` and is accepted for any practical input size supported by the required output.

The useful observation is that the surviving numbers have a fixed pattern. Every group

`3k + 1, 3k + 2, 3k + 3`

contains exactly two surviving values, namely `3k + 1` and `3k + 2`. We can use this structure to compute the `i`-th survivor directly instead of checking candidates one by one.

For one-based index `i`, the number of destroyed multiples of `3` before the `i`-th survivor is exactly `floor((i - 1) / 2)`. Adding those destroyed numbers to the survivor's one-based position gives

`answer(i) = i + floor((i - 1) / 2)`.

For example, when `i = 5`, we get `5 + 2 = 7`. When `i = 6`, we get `6 + 2 = 8`. The formula produces the sequence directly.

Both methods are linear because the output itself has `n` lines. The formula-based solution is preferable because every printed value is computed in constant time and the structure of the sequence is explicit.

| Approach | Time Complexity | Space Complexity | Verdict |
| --- | --- | --- | --- |
| Brute Force | O(n) | O(1) apart from output buffering | Accepted |
| Optimal | O(n) | O(1) apart from output buffering | Accepted |

## Algorithm Walkthrough

1. Read `n`, the number of survivors required.
2. For each one-based position `i` from `1` through `n`, compute `i + (i - 1) // 2`. The added term counts how many multiples of `3` have appeared before this survivor, so it shifts the survivor to its actual position among all positive integers.
3. Append each computed value to the output and print all values together. Since there must be exactly `n` output lines, producing each answer once gives the required linear running time.

### Why it works

Consider the positive integers divided into blocks of three:

`1, 2, 3`, `4, 5, 6`, `7, 8, 9`, and so on.

Each block contributes its first two numbers and destroys its third number. Before the survivor at one-based position `i`, exactly `(i - 1) // 2` destroyed numbers have been skipped. Thus its value among all positive integers is its survivor position `i` plus exactly that many skipped values. The formula `i + (i - 1) // 2` consequently produces every survivor in increasing order, with no multiple of `3` included and no surviving positive integer omitted.

## Python Solution

```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())

    ans = []
    for i in range(1, n + 1):
        ans.append(str(i + (i - 1) // 2))

    sys.stdout.write("\n".join(ans))

if __name__ == "__main__":
    solve()
```

The loop uses one-based indexing because the mathematical formula is naturally expressed in terms of the first survivor, the second survivor, and so on. For `i = 1`, the formula gives `1`, which handles the smallest valid input without a special case.

The expression `(i - 1) // 2` is the key implementation detail. Using `i // 2` would shift every odd-indexed survivor incorrectly. For example, at `i = 3`, the correct answer is `4`, while `3 + 3 // 2` would produce `4` by coincidence, but at `i = 5`, the correct expression gives `7`, whereas using a different rounding convention can introduce an error. The subtraction before integer division directly represents the number of complete survivor pairs preceding position `i`.

Python integers have arbitrary precision, so there is no integer-overflow issue. The answer itself is only about `1.5n`, and storing the output strings is linear in the output size.

## Complexity Analysis

| Measure | Complexity | Explanation |
| --- | --- | --- |
| Time | O(n) | Each of the `n` required answers is computed once and written once. |
| Space | O(n) | The implementation stores the `n` output strings before writing them. |

The linear time is optimal because the output itself contains `n` separate integers. The arithmetic for each answer is constant time, and the solution performs no search, sorting, simulation state, or auxiliary data-structure operations. The memory can also be reduced to `O(1)` auxiliary space by writing incrementally, but collecting the output is usually faster in Python because it reduces the number of write calls.

## Edge Cases

For `n = 1`, the input is

```
1
```

The loop runs once with `i = 1`. The skipped-count term is `(1 - 1) // 2 = 0`, so the answer is `1 + 0 = 1`. The output is therefore exactly `1`, and the destroyed value `0` never enters the positive-integer sequence.

For `n = 3`, the input is

```
3
```

The three iterations produce `1`, `2`, and `4`. The third value is larger than `3` because `3` is destroyed. The formula accounts for that with `(3 - 1) // 2 = 1`, giving `3 + 1 = 4`.

For `n = 5`, the input is

```
5
```

The generated values are `1, 2, 4, 5, 7`. The transition from `5` to `7` exercises the same rule again: `6` is a multiple of `3`, so one destroyed value must be skipped before the fifth survivor.

For a large input such as

```
100000
```

the final answer is

`100000 + 99999 // 2 = 149999`.

There are exactly `49,999` multiples of `3` from `1` through `149999`, so removing those from the `149999` positive integers leaves `100000` survivors. The formula thus handles the large boundary without any special treatment.
