## Solution
## Problem Understanding

The problem asks us to generate the usual FizzBuzz sequence over an integer interval. We are given two integers, `a` and `b`, and must process every integer starting at `a` and stopping before `b`. For each integer, we normally print the integer itself. A multiple of 3 becomes `Fizz`, a multiple of 5 becomes `Buzz`, and a multiple of both becomes `FizzBuzz`. Each result is printed on its own line. The official problem uses an inclusive lower bound and an exclusive upper bound.

The interval contains exactly `b - a` integers when `a < b`. There is no need for a data structure, preprocessing, or a sophisticated mathematical technique because the output itself contains one line for every integer in the interval. If the interval contains `k` values, any correct program has to produce `k` lines, so an algorithm that spends constant work per value is already asymptotically optimal. The stated time limit is 1 second and the memory limit is 256 MB, so the implementation should avoid unnecessary storage and construct the output efficiently.

The first edge case is a value divisible by both 3 and 5. For input

```
15
16
```

the correct output is

```
FizzBuzz
```

A careless implementation that checks `n % 3 == 0` before checking divisibility by 5 might print only `Fizz`. The combined case must be handled first, or equivalently both strings must be accumulated before printing.

The second edge case is the exclusive upper boundary. For input

```
11
18
```

the values processed are 11 through 17, so the output ends with `17`. The number `18` must not be printed. A loop written as `range(a, b + 1)` silently introduces an off-by-one error. The correct Python range is `range(a, b)`. This behavior is also visible in the official second sample.

The third edge case is a value divisible by neither number. For input

```
1
3
```

the output is

```
1
2
```

The program must print the original integer when neither divisibility condition applies. Replacing every value with a string unconditionally, or printing nothing unless a multiple is found, would produce the wrong result.

## Approaches

The direct approach is to visit every integer from `a` through `b - 1` and determine what should be printed. For each value, two modulo operations are enough to determine whether it is divisible by 3 and 5. If both conditions hold, we print `FizzBuzz`; otherwise we print whichever individual replacement applies, and if neither applies, we print the number itself. This is correct because the replacement rule depends only on the current integer, so every output line can be determined independently.

A brute-force implementation and the optimal implementation are effectively the same here. There is no hidden search space to optimize. If the interval contains `k = b - a` integers, the output itself has `k` lines. Even an imagined algorithm that somehow decided all replacements without inspecting the values would still have to spend Ω(k) time writing those lines. The direct simulation uses O(k) time, which matches that unavoidable lower bound.

The key observation is that this is one of the cases where simulation is already optimal. The divisibility tests are constant-time, and the problem asks us to output every position rather than summarize the result. Trying to derive a formula for the number of Fizz or Buzz values would not help because we still have to print their exact sequence.

| Approach | Time Complexity | Space Complexity | Verdict |
| --- | --- | --- | --- |
| Brute Force | O(b - a) | O(1), excluding output storage | Accepted |
| Optimal | O(b - a) | O(b - a) if output is buffered | Accepted |

The distinction between the two rows is conceptual rather than algorithmic. The straightforward simulation is already the optimal asymptotic solution.

## Algorithm Walkthrough

1. Read `a` and `b`. The interval we need to process is `[a, b)`, so `a` is included and `b` is excluded.
2. Iterate through every integer `x` in `range(a, b)`. Each iteration corresponds to exactly one required output line.
3. Check whether `x` is divisible by both 3 and 5. If so, produce `FizzBuzz`. This condition must be considered before the individual cases because a multiple of 15 satisfies both divisibility tests.
4. Otherwise, check whether `x` is divisible by 3. Produce `Fizz` when it is.
5. Otherwise, check whether `x` is divisible by 5. Produce `Buzz` when it is.
6. If none of the divisibility conditions holds, produce the decimal representation of `x`.
7. Print all generated lines in their original order. Buffering the lines avoids repeatedly invoking `print`, while still using memory proportional only to the required output.

The invariant is simple: after processing the first `i` values of the interval, the output contains exactly the correct FizzBuzz representation of those `i` values in the same order. For the next value, the mutually exclusive decision sequence considers the both-divisible case first and then the individual cases, so its representation is correct. Adding that representation preserves the invariant until every value in `[a, b)` has been processed.

## Python Solution

```python
import sys
input = sys.stdin.readline

def solve():
    a = int(input())
    b = int(input())

    ans = []

    for x in range(a, b):
        if x % 15 == 0:
            ans.append("FizzBuzz")
        elif x % 3 == 0:
            ans.append("Fizz")
        elif x % 5 == 0:
            ans.append("Buzz")
        else:
            ans.append(str(x))

    sys.stdout.write("\n".join(ans))

if __name__ == "__main__":
    solve()
```

The two input lines are read separately because the statement specifies two line-separated integers.

The loop uses `range(a, b)`, which exactly models the required inclusive-exclusive interval. Using `range(a, b + 1)` would incorrectly process `b`.

Testing divisibility by 15 first is equivalent to testing divisibility by both 3 and 5, since 15 is their least common multiple. It also makes the priority of `FizzBuzz` explicit. Once that case fails, the `elif` chain guarantees that only one of `Fizz`, `Buzz`, or the original number is selected.

The answer is accumulated in a list and written once. This avoids the overhead of a separate output operation for every number. The list is not required for the algorithmic idea, but it is a practical Python implementation choice for large output.

Python integers do not overflow, so there is no special integer-width handling required.

## Edge Cases

For the combined divisibility case, consider

```
15
16
```

The loop processes only `x = 15`. Since `15 % 15 == 0`, the first condition succeeds and the program appends `FizzBuzz`. The output is exactly `FizzBuzz`. Checking the 3-divisibility case first would incorrectly produce `Fizz`, which is why the order of conditions matters.

For the exclusive upper boundary, consider

```
11
18
```

The loop visits 11, 12, 13, 14, 15, 16, and 17. It never visits 18 because Python's `range(a, b)` excludes `b`. The final output is

```
11
Fizz
13
14
FizzBuzz
16
17
```

A loop ending at `b + 1` would incorrectly append `Fizz` for 18.

For a value that matches neither divisibility rule, consider

```
1
3
```

The loop visits 1 and 2. Neither is divisible by 3 or 5, so both values fall through to the final `else` branch. The output is

```
1
2
```

This confirms that the algorithm does not treat FizzBuzz as a filtering operation. Every input integer must produce exactly one output line, either a replacement string or the original number.

The central lesson from this problem is that not every FizzBuzz task needs a mathematical shortcut. Here, the required output contains every value in the requested interval, so direct simulation is already optimal. The cleanest solution is simply to respect the interval boundary and apply the divisibility rules in the correct priority order.
