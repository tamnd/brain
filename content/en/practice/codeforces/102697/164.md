## Solution
## Problem Understanding

Arseny has an unlimited supply of 100-ruble notes and starts with `m` one-ruble coins. On day `i`, he must pay at least `c_i` rubles. The cashier gives change whenever he pays too much, and the dissatisfaction for that day is the number of individual notes and coins returned, multiplied by `w_i`. The goal is to choose how many notes and coins to pay each day so that the total dissatisfaction is minimum. Coins received as change remain available on later days.

The part divisible by 100 is never interesting. If `c_i = 100q + r`, where `0 <= r < 100`, we can always pay `q` notes and deal separately with the remaining `r` rubles. When `r > 0`, there are exactly two useful ways to handle that remainder. We can pay `r` coins, which produces no change, or we can pay one additional 100-ruble note and receive `100-r` coins as change. The latter costs `(100-r) * w_i` dissatisfaction.

The constraints allow `n` to reach `100000`, while each price and weight is at most `100000`. A quadratic algorithm would already perform around `10^10` operations in the worst case, far beyond a one-second limit. We need an `O(n log n)` or better solution. The fact that every relevant coin amount is below 100 is the key structural simplification.

A first edge case is an exact multiple of 100. For example,

```
1 01007
```

has answer `0`, with payment `1 0`. A careless implementation might treat every day as having a choice between exact payment and paying one extra note, but paying the extra note here creates a 100-ruble change consisting of one note, which is strictly worse than exact payment.

A second edge case is having exactly enough coins. For example,

```
1 501503
```

has answer `0`, with payment `1 50`. Testing `m > r` instead of `m >= r` would incorrectly make the cashier receive change.

A third edge case is when the current day is short of coins, but an earlier day can be changed retroactively. Consider

```
3 0150 50 1501 1 100
```

On the first day, we must receive 50 coins. On the second day, we can spend those 50 coins exactly. On the third day, we are again short. It is better to have changed the second day to a 100-ruble note and received 50 coins, because that replacement costs only `50`, whereas receiving 50 coins on the third day costs `5000`. A greedy algorithm that only considers the current day would miss this exchange.

## Approaches

The direct brute-force approach is to consider both possible actions for every day with a nonzero remainder. One action pays the remainder with coins, and the other pays one extra note and receives change. For every complete sequence of choices, we can simulate the coin balance and calculate the dissatisfaction. This is correct because these two actions cover every useful way to handle the part below 100, but there can be up to `2^n` different choices. With `n = 100000`, that is `2^100000` possibilities, so enumeration is completely infeasible.

The useful observation is that paying a remainder with coins creates an opportunity that can be revoked later. Suppose day `i` has remainder `r`. If we currently pay `r` coins, then we can later change that decision to paying one additional 100-ruble note instead. Relative to the original decision, our coin balance increases by exactly 100, while the additional dissatisfaction is `(100-r) * w_i`.

That last quantity can be viewed as the **cost of buying 100 additional coins from day `i`**. Every time we pay a remainder using coins, we store this potential future purchase in a priority queue.

Now suppose a later day has remainder `r` but fewer than `r` coins are available. We have exactly two meaningful options. We can pay an additional note today and suffer `(100-r) * w_i`, or we can undo one earlier exact payment. Undoing any earlier payment gives us exactly 100 extra coins, which is enough to pay the current remainder because `r < 100`.

Since only one earlier payment needs to be undone, the best earlier payment is the one with the smallest replacement cost. A min-heap gives us that candidate in `O(log n)` time. If its cost is smaller than the cost of taking change today, we undo it. Otherwise, we accept change today.

This is the central greedy exchange. When a shortage appears, either buy the required 100 coins now or buy them by replacing the cheapest earlier purchase. There is no reason to replace an earlier payment with a more expensive one.

| Approach | Time Complexity | Space Complexity | Verdict |
| --- | --- | --- | --- |
| Brute Force | `O(2^n * n)` | `O(n)` | Too slow |
| Greedy + Min-Heap | `O(n log n)` | `O(n)` | Accepted |

## Algorithm Walkthrough

1. For every price, split it as `c_i = 100q_i + r_i`. Initially plan to pay `q_i` notes. Only `r_i` affects the coin management.
2. If `r_i = 0`, pay exactly `q_i` notes. There is no useful reason to involve coins because the price is already a multiple of 100.
3. If there are at least `r_i` coins, pay `q_i` notes and `r_i` coins. The coin balance decreases by `r_i`, and this day creates a candidate for a future replacement. The cost of replacing this exact payment by one extra note is `(100-r_i) * w_i`, so insert that cost together with the day index into a min-heap.
4. If there are fewer than `r_i` coins, the current exact payment is impossible. The current alternative is to pay `q_i + 1` notes and receive `100-r_i` coins. Its dissatisfaction is `(100-r_i) * w_i`.
5. Before accepting that cost, inspect the cheapest candidate in the heap. Replacing that earlier exact payment by one extra note gives exactly 100 more coins. Since `r_i < 100`, those 100 coins are enough to pay the current remainder exactly.
6. If the cheapest previous replacement costs less than the current day's change, remove that candidate from the heap, mark its day as paid with one extra note, add its cost to the answer, add 100 to the current coin balance, and then spend `r_i` coins on the current day.
7. Otherwise, keep all previous decisions unchanged. Pay one extra note today, receive `100-r_i` coins, add `(100-r_i) * w_i` to the answer, and mark today's payment as using the extra note.
8. Whenever a day is paid exactly with coins, insert its replacement cost into the heap. If that day is later replaced, remove its candidate from the heap. The heap thus contains exactly the earlier exact payments that are still available for replacement.

The key invariant is that every heap entry represents a previous day whose payment can be changed from `r` coins to one additional 100-ruble note, producing exactly 100 more coins at the stored dissatisfaction cost. Whenever the current day lacks enough coins, replacing any one such day makes the current payment feasible. Choosing the cheapest available replacement is optimal because all replacements provide the same 100 additional coins, so only their costs differ. If the cheapest previous replacement is not cheaper than accepting change today, changing the current day is at least as good as changing any previous day.

## Python Solution

```python
Pythonimport sysimport heapq
input = sys.stdin.readline

def solve():    n, m = map(int, input().split())    c = list(map(int, input().split()))    w = list(map(int, input().split()))
    notes = [x // 100 for x in c]    rem = [x % 100 for x in c]
    extra = [False] * n    heap = []    answer = 0
    for i in range(n):        r = rem[i]
        if r == 0:            continue
        current_cost = (100 - r) * w[i]
        if m >= r:            m -= r            heapq.heappush(heap, (current_cost, i))            continue
        if not heap or heap[0][0] >= current_cost:            m += 100 - r            answer += current_cost            extra[i] = True            continue
        old_cost, old_i = heapq.heappop(heap)
        extra[old_i] = True        answer += old_cost
        m += 100        m -= r
        heapq.heappush(heap, (current_cost, i))
    out = [str(answer)]
    for i in range(n):        if extra[i]:            out.append(f"{notes[i] + 1} 0")        else:            out.append(f"{notes[i]} {rem[i]}")
    sys.stdout.write("\n".join(out))

if __name__ == "__main__":    solve()
```

The arrays `notes` and `rem` separate the unavoidable 100-ruble part from the part that needs coins. For a day marked in `extra`, the code adds exactly one note to `notes[i]` and uses zero coins. Otherwise it uses the original number of notes and exactly `rem[i]` coins.

The heap stores `(replacement_cost, day_index)`. Python's `heapq` is a min-heap, so `heap[0]` is automatically the cheapest previous payment that can be replaced.

When a previous day is replaced, the current coin balance receives `100` additional coins relative to the original exact-payment history. The code then immediately subtracts the current remainder `r`. Since `r < 100`, the resulting balance is nonnegative.

The comparison uses `>=` when deciding whether to replace an earlier day. If the two costs are equal, keeping the earlier decision and taking change today is already optimal, so either choice is valid.

Python integers have arbitrary precision, which is useful because the total dissatisfaction can reach roughly `100 * 10^5 * 10^5`, well above the range of a signed 32-bit integer.

The first shortage occurs on day 2. Its change cost is 29, cheaper than replacing day 1 for 83, so day 2 takes change. The final cost is `29 + 50 = 79`. The corresponding payments are `1 17`, `1 0`, `2 0`, `2 43`, `2 0`, matching the sample output.

## Complexity Analysis

| Measure | Complexity | Explanation |
| --- | --- | --- |
| Time | `O(n log n)` | Each nonzero remainder is inserted into the heap once and can be removed at most once. |
| Space | `O(n)` | The heap and output information contain at most one entry per day. |

With `n <= 100000`, `O(n log n)` means roughly a few million heap operations at most, which is appropriate for the one-second constraint in compiled languages and remains practical in Python with a lightweight `heapq` implementation. The official limit is 1 second and 256 MB.

## Edge Cases

For an exact multiple of 100,

```
1 01007
```

the remainder is zero. The algorithm skips the heap completely and pays one note. The output is `0` followed by `1 0`. This avoids the common mistake of treating a zero remainder as though paying an extra note could somehow help.

For exactly enough coins,

```
1 501503
```

the initial balance is 50 and the remainder is also 50. The condition `m >= r` succeeds, so the algorithm pays one note and 50 coins. No change is created and the answer is zero. The equality in this condition is essential.

For one coin too few,

```
1 491501
```

the exact payment is impossible. There is no previous heap entry, so the only choice is to pay two notes and receive 50 coins. The dissatisfaction is `50 * 1 = 50`, giving output cost `50`, with payment `2 0`.

For the more interesting exchange case,

```
3 0150 50 1501 1 100
```

day 1 has no coins, so it pays two notes and receives 50 coins at cost 50. Day 2 spends those 50 coins exactly, while its replacement cost is also 50. On day 3 there are no coins again, and taking change would cost `50 * 100 = 5000`. The heap contains day 2 with replacement cost 50, so the algorithm replaces day 2 instead. This gives 100 extra coins relative to the previous state, allowing day 3 to pay its 50-coin remainder exactly. The final cost is 100 rather than 5050, demonstrating why decisions from earlier days must remain available for later greedy exchanges.

The invariant behind all of these cases is the same: an exact payment recorded in the heap can be converted into one extra 100-ruble note, producing exactly 100 additional coins at a known cost. Since every remainder is strictly below 100, one such conversion is enough to repair any single coin shortage. The heap always chooses the cheapest conversion, which is precisely the exchange needed to keep the total dissatisfaction minimum.
