## Solution
## Problem Understanding

The task is to find the smallest integer that is at least the given number (n), using only the decimal digits 4 and 7, with exactly the same number of 4s and 7s. Such a number is called super lucky. The input contains one positive integer, but its value can have up to 100,000 decimal digits, so it must be treated as a string rather than converted to a machine integer. The output is the smallest super lucky number satisfying the lower bound.

The length of a super lucky number must be even, because its digits have to split equally between 4 and 7. If the input length is odd, no super lucky number of that length exists, so the answer immediately has to use the next even length. With 100,000 digits, enumerating candidates is completely impossible. There are (2^{100000}) strings made only from 4 and 7, and even restricting ourselves to balanced strings leaves (\binom{100000}{50000}) candidates. The intended solution has to process the decimal representation in linear time. The original problem has a 2 second time limit and allows (n) to have 100,000 digits.

There are several cases where a careless implementation can silently go wrong. For input `47`, the number itself is already super lucky, so the correct output is `47`. An implementation that always searches for a strictly larger number would incorrectly produce `74`.

For input `1`, the length is odd. There cannot be a balanced lucky number with one digit, so the answer is the smallest balanced lucky number with two digits, `47`. An implementation that only searches among numbers having the same length would fail here.

For input `4500`, the correct output is `4747`. The first digit can stay equal to 4, but the second digit 5 cannot be used in a lucky number. We have to increase that position to 7 and then fill the remaining positions with one 4 and one 7. A solution that only considers changing an existing 4 into 7 would miss the possibility of replacing an invalid digit such as 5 with 7.

For input `7777`, no four-digit super lucky number can be at least the input. Every possible change at the beginning would leave too many 7s in the prefix, so the answer moves to the next even length and becomes `444777`. An implementation that assumes a same-length answer always exists would either construct an invalid number or run past the beginning of the string.

## Approaches

A direct brute-force solution would generate every lucky number of the relevant length, keep the ones containing equally many 4s and 7s, and choose the first one that is at least (n). For a length (L), there are exactly (2^L) strings containing only 4 and 7. In the worst case (L=100000), that means exactly (2^{100000}) candidates, before even checking whether their digit counts are balanced. If we generate only balanced candidates, their number is still (\binom{100000}{50000}), which is astronomically large. Checking each candidate against (n) can itself require (O(L)) character comparisons. The brute-force approach is correct because it explicitly examines the entire candidate set, but its exponential growth makes it unusable.

The useful observation is that we do not need to construct candidates independently. All super lucky numbers of the same length have exactly half their positions occupied by 4 and half by 7. When comparing two equal-length numbers, the first position where they differ determines which one is smaller. That means we should keep the prefix equal to (n) for as long as possible. At the first position where equality can no longer continue, we want to increase that digit by the smallest possible amount, then make the suffix as small as possible.

There are only two lucky digits, so at any position there is at most one useful larger digit. If the input digit is 4, we can replace it with 7. If the input digit is 0 through 3, we can replace it with 4. If the input digit is 5 or 6, we can replace it with 7. If it is 7, 8, or 9, there is no lucky digit larger than it. Once a position is increased, the suffix should contain all remaining 4s before all remaining 7s, because 4 is the smaller digit.

The subtle part is choosing the position to increase. A later position is always preferable to an earlier one because it preserves a longer prefix equal to (n). While scanning from left to right, we can remember the latest position at which increasing the current digit was feasible while keeping the digit counts within their required limits. If the original number is already super lucky, we return it immediately. If no feasible increase exists, there is no same-length answer, so we use the smallest super lucky number with the next even length.

| Approach | Time Complexity | Space Complexity | Verdict |
| --- | --- | --- | --- |
| Brute Force | O(L · 2^L) | O(L) | Too slow |
| Optimal | O(L) | O(L) | Accepted |

## Algorithm Walkthrough

1. Read (n) as a string and let its length be (L). We never convert it to an integer because (L) can be 100,000, far beyond normal machine integer ranges.
2. If (L) is odd, increase it by one and construct the smallest super lucky number of that length. Since 4 is smaller than 7, that number is a block of (L/2) 4s followed by (L/2) 7s. An odd-length number can never contain equal counts of the two digits.
3. If (L) is even, first check whether (n) itself contains only 4 and 7 and exactly (L/2) copies of each. If it does, it is already the smallest possible answer because the required value is at least (n).
4. Scan the digits from left to right while maintaining the number of 4s and 7s in the prefix. At position (i), the prefix before (i) must consist entirely of lucky digits. If an invalid digit has already appeared, no later position can be used as the first changed position because the unchanged prefix would contain that invalid digit.
5. At the current position, determine the smallest lucky digit strictly greater than (n[i]). For a digit below 4 this is 4, for 5 or 6 it is 7, and for 4 it is 7. Digits 7, 8, and 9 have no larger lucky digit.
6. Check whether placing that larger digit would make either digit count exceed (L/2). If it is feasible, remember this position and the replacement digit. We deliberately keep scanning because a later feasible position produces a smaller final number by preserving more of the original prefix.
7. After the scan, if a feasible position was found, copy the prefix before that position, put the remembered larger digit there, and fill the remaining positions with exactly the required number of 4s followed by exactly the required number of 7s. This suffix is lexicographically smallest because every 4 is smaller than every 7.
8. If no feasible position exists, construct the smallest super lucky number with length (L+2). Every number with more digits is larger than every (L)-digit number, so this is the correct fallback.

The invariant is that every remembered candidate has a prefix identical to (n), followed by the first position where the candidate becomes larger. Its digit counts can still be completed to exactly (L/2) copies of each digit. Among all such candidates, the latest changed position has the longest common prefix with (n), so it is the smallest. Once that position is fixed, putting all remaining 4s before all remaining 7s gives the smallest possible suffix. If no such position exists, no same-length super lucky number can be at least (n), so increasing the length is unavoidable.

## Python Solution

```python
import sys
input = sys.stdin.readline

def solve(n: str) -> str:
    length = len(n)

    # An odd length cannot contain equal numbers of 4 and 7.
    if length % 2 == 1:
        half = (length + 1) // 2
        return '4' * half + '7' * half

    half = length // 2

    # If n is already super lucky, it is the answer.
    if n.count('4') == half and n.count('7') == half:
        return n

    count4 = 0
    count7 = 0

    best_pos = -1
    best_digit = ''

    for i, ch in enumerate(n):
        if ch not in '47':
            # Find the smallest lucky digit strictly greater than ch.
            if ch < '4':
                digit = '4'
            elif ch < '7':
                digit = '7'
            else:
                digit = ''

            if digit:
                new4 = count4 + (digit == '4')
                new7 = count7 + (digit == '7')

                if new4 <= half and new7 <= half:
                    best_pos = i
                    best_digit = digit

            # The unchanged prefix would contain an invalid digit,
            # so no later position can be the first changed position.
            break

        # ch is lucky. It can only be increased if it is 4.
        if ch == '4':
            if count4 <= half and count7 + 1 <= half:
                best_pos = i
                best_digit = '7'
            count4 += 1
        else:
            count7 += 1

    if best_pos == -1:
        # No valid answer with the same length.
        new_length = length + 2
        half = new_length // 2
        return '4' * half + '7' * half

    # Use the longest possible unchanged prefix.
    prefix = n[:best_pos]
    new4 = count4
    new7 = count7

    # The counts above correspond to the prefix when best_pos is after
    # the scan, so recompute them directly for the chosen prefix.
    new4 = prefix.count('4')
    new7 = prefix.count('7')

    if best_digit == '4':
        new4 += 1
    else:
        new7 += 1

    remaining4 = half - new4
    remaining7 = half - new7

    return prefix + best_digit + '4' * remaining4 + '7' * remaining7

def main():
    n = input().strip()
    print(solve(n))

if __name__ == "__main__":
    main()
```

The first branch handles odd lengths before doing any detailed comparison. The new length is the smallest even length larger than the input length, and the lexicographically smallest string with equal counts is all 4s followed by all 7s.

The exact-match check uses the fact that a super lucky number of even length must contain exactly `half` copies of both digits. Returning immediately prevents the greedy search from unnecessarily producing a strictly larger number.

During the main scan, `count4` and `count7` describe the unchanged prefix before the current position. When the current digit is 4, changing it to 7 is the only possible way to make the number larger while keeping it lucky. When the current digit is not lucky, the code tries the smallest lucky digit that exceeds it. The scan stops after the first invalid digit because any later candidate would have to leave that invalid digit unchanged.

The `best_pos` variable stores the latest feasible increase. Storing the latest rather than the first one is the key greedy choice. A later change preserves more digits from the original number, making the resulting number smaller.

After the scan, the code reconstructs the suffix using the remaining number of 4s followed by the remaining number of 7s. The implementation uses string operations throughout, so it never performs arithmetic on a 100,000-digit integer. Python's integer conversion limits are consequently irrelevant.

The `prefix.count` calls occur only once after the candidate position has been chosen, so they add at most another linear pass. The total running time remains linear. The use of Python booleans in expressions such as `digit == '4'` is intentional, since `True` and `False` behave as 1 and 0 when added to the counts.

## Worked Examples

For the first sample, `n = 4500`, the length is 4 and half is 2. The number itself is not super lucky because its digits are not all 4 and 7. The scan proceeds as follows.

| Position | Digit | 4s before | 7s before | Possible larger lucky digit | Feasible candidate |
| --- | --- | --- | --- | --- | --- |
| 0 | 4 | 0 | 0 | 7 | 7 |
| 1 | 5 | 1 | 0 | 7 | 7 |

At position 0, changing 4 to 7 gives a valid candidate, but we continue because a later change is preferable. At position 1, the digit 5 can also become 7, and the prefix `4` leaves enough capacity for the remaining digits. The best position is therefore 1. The prefix is `4`, the changed digit is `7`, and the remaining counts require one 4 and one 7, giving `4747`. This matches the official sample.

For the second sample, `n = 47`, the length is 2 and half is 1. Both digits are lucky and their counts are already equal.

| Position | Digit | 4s after reading | 7s after reading | Status |
| --- | --- | --- | --- | --- |
| 0 | 4 | 1 | 0 | Prefix remains valid |
| 1 | 7 | 1 | 1 | Exactly balanced |

Since the input itself satisfies every condition, the algorithm returns `47` without constructing a larger candidate. This demonstrates why the equality case must be checked before applying the strict-increase greedy step.

## Edge Cases

For the odd-length case, consider the exact input `1`. Its length is 1, so equal numbers of 4s and 7s are impossible. The algorithm immediately changes the target length to 2 and constructs one 4 followed by one 7. The output is `47`, which is the smallest possible super lucky number and is greater than `1`.

For an input that is already super lucky, consider `47`. The algorithm counts one 4 and one 7, matching the required half-length of 1 for both digits. It returns the input unchanged. This prevents the greedy construction from unnecessarily making the answer larger.

For an invalid digit that can be replaced directly, consider `4500`. At position 0, changing 4 to 7 is feasible, so `best_pos` becomes 0. At position 1, the digit 5 can be replaced by 7 while the prefix `4` remains valid and the digit counts can still be completed. Since position 1 is later, it replaces the previous candidate. The suffix needs one 4 and one 7, producing `4747`.

For an invalid digit that is too large to replace directly, consider `4788`. At position 0, changing 4 to 7 is feasible. Positions 1 and later cannot be used after the first invalid digit because the unchanged prefix would contain 8. The algorithm keeps the candidate at position 0, giving the prefix ``, changed digit `7`, and a suffix containing one 4 and one 7, so the result is `7447`. This is larger than `4788` and is the smallest valid four-digit candidate.

For a case where every same-length candidate is impossible, consider `7777`. The length is 4, so a valid answer would need two 4s and two 7s. There is no position containing 4 that can be increased, and changing any earlier 7 is impossible because 7 is already the largest lucky digit. No candidate is recorded, so the algorithm moves to length 6. The smallest six-digit super lucky number is `444777`, which is necessarily larger than every four-digit number and is thus the correct answer.
