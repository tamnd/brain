## Solution
## Problem Understanding

The problem classifies heart-rate measurements into one of five fitness zones. A student's maximum heart rate, abbreviated MHR, is defined as (220-\text{age}). Each recorded heart rate is then compared with that MHR.

Zone 5 contains readings from 90% through 100% of MHR. Zone 4 contains readings from 80% up to, but not including, 90%. Zone 3 covers 70% through less than 80%, Zone 2 covers 60% through less than 70%, and anything below 60% belongs to Zone 1. The task is to print the corresponding zone for every recorded heart rate. The official problem specifies the input as one age, followed by the number of readings and then those readings.

There is no need for a sophisticated data structure because every heart-rate value is independent of every other value. If there are (n) readings, we must inspect all (n) of them, giving a natural lower bound of (O(n)). An algorithm that repeatedly compares every pair of readings would unnecessarily require (O(n^2)) work and becomes unsuitable as the number of measurements grows.

The main numerical edge case is a heart rate exactly on a zone boundary. For example, with age 20, MHR is 200, so a reading of 180 is exactly 90% and must be printed as Zone 5, not Zone 4. Another boundary occurs at 160, which is exactly 80% and belongs to Zone 4. The same distinction applies at 140 and 120.

For example, the input

```
20
4
180
160
140
119
```

produces

```
Zone 5
Zone 4
Zone 3
Zone 1
```

A careless floating-point implementation can also make boundary handling unnecessarily fragile. The comparison (r \ge 90%\cdot MHR) can be rewritten as (10r \ge 9MHR), so every decision can be made with exact integer arithmetic.

A second edge case is a reading below 60%. With age 20 and MHR 200, a reading of 119 is 59.5%, so it belongs to Zone 1. Checking whether the integer percentage is at least 60 would be equivalent here, but computing the exact cross-multiplied comparison is safer and directly represents the stated percentage boundary.

## Approaches

The straightforward approach computes the student's MHR once, then processes every heart-rate measurement independently. For each reading, we can calculate its percentage of MHR and compare it against 90, 80, 70, and 60. This is correct because the zones are defined solely by these thresholds, and there is no interaction between measurements. Its worst-case work is proportional to the number of readings, with a constant amount of arithmetic and comparison per reading.

A slightly better implementation avoids floating-point arithmetic altogether. Suppose the measured heart rate is (r) and the MHR is (M). Instead of testing (r/M \ge 0.9), multiply both sides by (10M), obtaining (10r \ge 9M). The same transformation gives the other boundaries as (10r \ge 8M), (10r \ge 7M), and (10r \ge 6M).

The brute-force numerical calculation works because each measurement is independent, but floating-point percentages add precision concerns without providing any benefit. The observation that every threshold is a simple rational percentage lets us replace all divisions with integer multiplication. The resulting algorithm is still linear, but its comparisons are exact.

| Approach | Time Complexity | Space Complexity | Verdict |
| --- | --- | --- | --- |
| Floating-point classification | O(n) | O(1) besides input storage | Accepted |
| Integer threshold comparison | O(n) | O(1) besides input storage | Accepted |

## Algorithm Walkthrough

1. Read the student's age and compute `mhr = 220 - age`. The MHR is fixed for the entire input, so calculating it once avoids repeating the same operation for every measurement.
2. Read the number of heart-rate measurements. We process each measurement independently because the classification of one reading never affects another.
3. For a reading `r`, first test `10 * r >= 9 * mhr`. This is exactly the condition (r \ge 90%) of MHR, so satisfying it places the reading in Zone 5.
4. If the Zone 5 condition failed, test `10 * r >= 8 * mhr`. A value reaching 80% but not 90% belongs to Zone 4.
5. Continue with the 70% and 60% thresholds. The first threshold satisfied determines the zone because the checks are performed from the highest percentage downward.
6. If none of the four thresholds is satisfied, the reading is below 60% of MHR and belongs to Zone 1.

Why it works: for every reading, the algorithm checks exactly the four boundaries that divide the five zones. The first successful comparison identifies the highest applicable boundary, so the reading falls into exactly the corresponding interval. Integer cross multiplication is equivalent to the original percentage comparison, so it does not change any classification.

## Python Solution

```python
import sys
input = sys.stdin.readline

def solve():
    age = int(input())
    n = int(input())

    mhr = 220 - age

    ans = []

    for _ in range(n):
        r = int(input())
        x = 10 * r

        if x >= 9 * mhr:
            ans.append("Zone 5")
        elif x >= 8 * mhr:
            ans.append("Zone 4")
        elif x >= 7 * mhr:
            ans.append("Zone 3")
        elif x >= 6 * mhr:
            ans.append("Zone 2")
        else:
            ans.append("Zone 1")

    sys.stdout.write("\n".join(ans))

if __name__ == "__main__":
    solve()
```

The first two input operations read the student's age and the number of measurements. The value `mhr` is computed once because it is identical for every reading.

For each heart rate, `x = 10 * r` lets the program compare against integer multiples of MHR. The Zone 5 condition, for example, is `10 * r >= 9 * mhr`, which is mathematically identical to (r \ge 0.9MHR).

The `elif` ordering is deliberate. A reading at exactly 90% satisfies both the 90% and 80% comparisons, but it must be Zone 5, so the highest threshold must be checked first. The same reasoning applies at every other boundary.

Python integers have arbitrary precision, so the multiplication cannot overflow. With the input bounds of this problem, even fixed-width 64-bit integers would be sufficient, but Python's integer behavior makes the implementation straightforward.

The results are accumulated and written together at the end. This avoids performing a separate output operation for every reading.

## Edge Cases

For the 90% boundary, consider age 20 and a heart rate of 180. The MHR is 200, and (180/200=90%). The first comparison becomes (10\cdot180=1800) and (9\cdot200=1800), so the condition is true and the program prints `Zone 5`. A careless implementation using `>` instead of `>=` would incorrectly classify this reading as Zone 4.

For a value immediately below a boundary, consider the same age and a heart rate of 179. The value is 89.5% of MHR. The Zone 5 comparison fails because (1790<1800), while the Zone 4 comparison succeeds because (1790\ge1600). The correct output is `Zone 4`.

For the 60% boundary, age 20 gives MHR 200 and 120 is exactly 60%. The comparison (10\cdot120\ge6\cdot200) becomes (1200\ge1200), so the correct output is `Zone 2`. A strict `>` comparison would incorrectly send this value to Zone 1.

For a value just below 60%, use 119 with the same age. Here (10\cdot119=1190), which is smaller than (6\cdot200=1200), so none of the Zone 2 through Zone 5 conditions succeeds. The algorithm reaches the final `else` and prints `Zone 1`.

For repeated identical readings, every measurement is classified independently. If all readings are 120 for age 20, every output line is `Zone 2`. No state from an earlier measurement is carried into the next one.

The implementation also handles readings above 100% naturally. Such a reading satisfies the 90% comparison and is classified as Zone 5, which is the highest available zone.
