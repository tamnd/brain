## Solution
## Problem Understanding

We are given two positive integers in ordinary decimal notation. The operation does not add their decimal digits directly. Instead, each number is viewed in base 4. For every position, we add the two base-4 digits independently and keep only the remainder modulo 4. There is no carry from one position to the next. The resulting base-4 number is then converted back to decimal and printed.

For example, consider the first sample, where the numbers are 7 and 9. In base 4 they are `13` and `21`. The corresponding digits give `1 + 2 = 3` in the high position and `3 + 1 = 4`, which becomes `0`, in the low position. The result is `30` in base 4, which is 12 in decimal.

The published problem statement gives a one-second time limit and a 256 MB memory limit, but does not expose a numerical upper bound for the two input integers. The natural solution should consequently depend on the number of base-4 digits rather than on the magnitude of the numbers themselves. If an input has (d) base-4 digits, a solution taking (O(d)) operations is easily appropriate. An approach that enumerates values up to the magnitude of the inputs would instead be proportional to the numbers themselves and would become infeasible even for moderately large integers.

There are several edge cases that are easy to mishandle. The first is a digit sum that reaches 4. For input `7` and `9`, the base-4 forms are `13` and `21`, so the low digits produce 4 and must become 0. The correct output is `12`. A careless implementation using ordinary base-4 addition would produce `100` in base 4, or 16 in decimal, because it would propagate a carry.

A second edge case is when one number has fewer base-4 digits than the other. For example, input `1` and `16` gives `1` and `100` in base 4. The missing digits of the shorter number are implicitly zero, so the result is `101` in base 4, which is 17 in decimal. An implementation that only processes positions present in both representations can silently discard the remaining digits.

A third edge case occurs when every digit produces zero. For input `15` and `15`, both numbers are `33` in base 4. Each position gives (3+3=6), which becomes 2 after subtracting 4, so the result is `22` in base 4, or 10 in decimal. This catches the common mistake of treating the operation as ordinary addition or as a bitwise operation.

## Approaches

A straightforward brute-force interpretation is to construct the answer by trying every possible contribution at every base-4 position. At each position there are four possible digits in each input, giving 16 possible pairs, and we could explicitly consult the corresponding result digit. If the numbers contain (d) base-4 positions, this still requires processing every position, but it adds an unnecessary constant-size search at each position. More fundamentally, a brute-force approach that tries candidate decimal results or enumerates numbers up to the input values has a worst-case operation count proportional to the numeric magnitude, such as (O(\max(a,b))), which is unacceptable when the inputs contain many digits.

The brute-force perspective is useful because it reveals the only operation that matters at one position: given digits (x) and (y), the answer digit is simply ((x+y)\bmod 4). There is no dependency between neighboring positions. Ordinary addition is usually difficult to decompose because a carry connects one digit to the next, but this problem explicitly removes that connection by discarding every carry.

The key observation is therefore that we can process the numbers from least significant base-4 digit to most significant base-4 digit. The current digits are obtained with `% 4`, and removing them is done with integer division by 4. Once both current digits have been extracted, their sum modulo 4 is exactly the output digit for that position. We multiply that digit by the corresponding power of 4 and accumulate it into the answer.

The brute-force works because it eventually examines the same independent base-4 positions, but fails when it spends time considering possibilities that the digit-wise rule already determines. The observation that every position is independent lets us reduce the whole operation to one constant amount of work per base-4 digit.

| Approach | Time Complexity | Space Complexity | Verdict |
| --- | --- | --- | --- |
| Brute Force | O(max(a, b)) in a magnitude-based enumeration | O(1) | Too slow |
| Optimal | O(log₄(max(a, b))) | O(1) | Accepted |

## Algorithm Walkthrough

1. Read the two decimal integers (a) and (b). We keep them as integers because repeated division and remainder operations give their base-4 digits directly without needing to build strings.
2. Set `answer = 0` and `power = 1`. The variable `power` represents the value of the current base-4 position, starting with (4^0=1).
3. Extract the current base-4 digit of each number using `a % 4` and `b % 4`. These are exactly the least significant digits that have not yet been processed.
4. Compute `(a_digit + b_digit) % 4` and add that digit multiplied by `power` to the answer. Taking modulo 4 is the definition of the special addition rule, so no carry is generated.
5. Divide both input numbers by 4 using integer division. This removes the digits just processed and moves the next base-4 digits into the current position.
6. Multiply `power` by 4 because the next iteration works one base-4 position higher.
7. Repeat while at least one input still has an unprocessed digit. If one number reaches zero first, its remaining digits are treated as zero, which is exactly what ordinary positional notation requires.
8. Print the accumulated decimal answer. Since `answer` was constructed as a sum of decimal values of the resulting base-4 digits, no separate base conversion is needed.

Why it works: after each iteration, all base-4 positions below the current one have already been assigned exactly their required result digits. The current digits are independent because the operation never carries between positions. Thus `(a % 4 + b % 4) % 4` determines the correct digit for the current position, and dividing by 4 exposes the next position without changing any unprocessed digit. When both numbers become zero, every position has been processed, so the accumulated decimal value is exactly the requested result.

## Python Solution

```python
import sys
input = sys.stdin.readline

def solve():
    a = int(input())
    b = int(input())

    answer = 0
    power = 1

    while a > 0 or b > 0:
        da = a % 4
        db = b % 4

        result_digit = (da + db) % 4
        answer += result_digit * power

        a //= 4
        b //= 4
        power *= 4

    print(answer)

if __name__ == "__main__":
    solve()
```

The first two lines of `solve` read the decimal representations and convert them to integers. The algorithm then maintains two pieces of state: `answer`, which stores all result digits already processed, and `power`, which identifies the decimal value of the current base-4 position.

The expressions `a % 4` and `b % 4` extract the least significant base-4 digits. This works because every integer can be written as (4q+r), where (r) is one of 0, 1, 2, or 3. Integer division by 4 then replaces the number with (q), effectively removing that digit.

The result digit must be `(da + db) % 4`. Using ordinary `da + db` would be incorrect when the sum is at least 4 because the special operation discards the carry instead of propagating it.

The loop condition is `a > 0 or b > 0`, not `and`. This handles numbers with different numbers of base-4 digits. Once one number reaches zero, its future digits are all zero, while the other number may still contribute significant digits.

Python integers do not suffer from fixed-width overflow, so the accumulation of `answer` is safe. The algorithm also avoids constructing a base-4 string and then converting it back, which keeps the implementation direct and gives constant auxiliary space.

## Edge Cases

For the carry-discarding case, the exact input is:

```
7
9
```

The numbers are `13` and `21` in base 4. The low digits are 3 and 1, whose sum is 4, so the result digit is `4 % 4 = 0`. The next digits are 1 and 2, giving 3. The result is `30` in base 4, or 12 in decimal. The algorithm produces 12 because it computes each digit modulo 4 and never transfers anything to the next iteration.

For unequal base-4 lengths, consider:

```
1
16
```

The values are `1` and `100` in base 4. The first position uses digits 1 and 0 and produces 1. The first number then becomes zero, but the loop continues because the second number still contains digits. The remaining positions use zero from the first number, giving the result `101` in base 4, which is 17 in decimal. The `or` in the loop condition is what prevents the higher digits from being lost.

For repeated maximum digits, consider:

```
15
15
```

Both numbers are `33` in base 4. Each pair gives (3+3=6), and (6\bmod4=2). The resulting base-4 number is `22`, equal to (2\cdot4+2=10) in decimal. This case checks every position where the two input digits are individually as large as possible and confirms that the operation is modulo 4 rather than ordinary addition.

For zero result digits in the middle of a number, the same mechanism handles them without special cases. For example, `7` and `9` produce `30` in base 4, so the low position contributes nothing while the higher position contributes (3\cdot4). The algorithm still advances `power` after processing the zero digit, preserving the positional value of every later digit.
