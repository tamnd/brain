## Solution
## Problem Understanding

We have a target calorie count `n` and `k` available food items. Food item `i` contributes exactly `c[i]` calories, and each food item can be eaten any number of times. The task is to reach exactly `n` calories while minimizing the number of food items eaten.

The input contains `n`, followed by `k`, followed by the calorie value of each food item. The output is the smallest number of items whose calorie values add up to exactly `n`. The official problem uses a one-second limit and 256 MB of memory.

The crucial difficulty is that the food values are arbitrary. The easier version had fixed values of 500, 100, and 50, where taking as many large items as possible works. In the harder version, that greedy property disappears. For example, with target 600 and food values 500, 300, and 1, taking the largest possible item first gives 500 and then requires one hundred-calorie remainder to be filled with 100 copies of the one-calorie item. The optimal answer is instead two 300-calorie items, so the answer is 2.

The statement available on Codeforces does not expose numerical upper bounds for `n` or `k`, so an honest complexity discussion has to use the natural parameters `n` and `k`. The intended approach is the standard unbounded minimum-coin dynamic programming solution, whose running time is `O(nk)`. This is practical when the target is small enough for a one-dimensional array of size `n + 1`, which is the setting in which this problem is designed to be solved. The third sample, for example, asks about only 10,000 calories and has three food values.

There are several cases where an implementation can silently go wrong. Consider the greedy counterexample

```
600
3
500
300
1
```

The correct output is

```
2
```

because `300 + 300 = 600`. A greedy implementation that always takes the largest food first chooses 500 and then needs 100 copies of the one-calorie food, producing 101 items.

A second edge case is when the best answer uses a food item that is not the largest. For

```
10
3
6
4
1
```

the answer is `2`, using `6 + 4`. A strategy based only on the largest denomination might start with 6 and then make a poor choice for the remainder, while the DP considers every possible last item.

A third issue is an exact-match boundary. For

```
12
2
6
4
```

the answer is `2`, not `3`, because `6 + 6` reaches the target directly. An implementation that only considers food values strictly smaller than the current remainder can miss this transition.

Finally, repeated use of a food item is allowed. For

```
9
2
3
5
```

the answer is `3`, using `3 + 3 + 3`. Treating every food item as usable at most once would incorrectly conclude that 9 cannot be formed.

## Approaches

The direct brute-force approach is to try every possible collection of food items and keep the smallest number whose total is exactly `n`. One way to implement this is recursive search: at each state, choose one of the `k` food types and continue until the accumulated calories reach or exceed the target. This is correct because every possible sequence of choices is explored, so an optimal combination cannot be missed.

The problem is that this search repeatedly explores the same subproblems. If the smallest food item has one calorie, a solution may require up to `n` choices. An ordered recursive search can have as many as `k^n` choice sequences in the worst case. Even when combinations rather than orderings are enumerated, the number of possibilities grows polynomially with degree depending on `k`, which quickly becomes infeasible.

The brute-force works because every solution can be represented as a sequence of food choices, but it fails because the same remaining calorie amount can be reached through many different prefixes. Suppose two different sets of foods have already produced 300 calories. From that point onward, the optimal way to make another 500 calories is completely independent of how those 300 calories were obtained. We should solve that remaining problem once and reuse its answer.

That observation leads directly to dynamic programming. Let `dp[x]` be the minimum number of food items required to make exactly `x` calories. For every reachable amount `x`, adding a food with `c` calories produces `x + c`, and the resulting solution uses one more item. Thus the transition is

`dp[x] = min(dp[x], dp[x - c] + 1)`

for every food value `c` not exceeding `x`.

This is an unbounded knapsack or minimum-coin-change problem. A food can be used repeatedly, so after computing `dp[x - c]`, we are allowed to use the same `c` again when computing `dp[x]`. Since every transition goes from a smaller calorie total to a larger one, processing totals from 0 through `n` gives all required states in dependency order.

| Approach | Time Complexity | Space Complexity | Verdict |
| --- | --- | --- | --- |
| Brute Force | Exponential in the worst case | O(n) recursion depth | Too slow |
| Optimal DP | O(nk) | O(n) | Accepted |

## Algorithm Walkthrough

1. Read the target `n` and the `k` food calorie values. Each value represents a food type that may be used repeatedly.
2. Create an array `dp` of length `n + 1`. Set every entry to infinity except `dp[0] = 0`.

The state `dp[x]` means that we already know the minimum number of food items needed to produce exactly `x` calories. Zero calories require zero food items, which gives the base case.
3. Process calorie totals `x` from 1 through `n`.

Every valid way to make `x` calories has some final food item. If that final item has `c` calories, the food eaten before it must have contributed exactly `x - c` calories. This means every optimal solution is represented by one of the transitions considered below.
4. For every food value `c` with `c <= x`, update

```
dp[x] = min(dp[x], dp[x - c] + 1)
```

We add one item to an optimal solution for `x - c`. If `x - c` is unreachable, its infinity value prevents that transition from affecting the answer.

1. After all totals have been processed, output `dp[n]`.

Because every state depends only on smaller calorie totals, all possible final food choices have already been considered by the time `dp[n]` is computed.

### Why it works

Consider an optimal solution for some reachable total `x`. Look at the final food item in that solution and let its calorie value be `c`. Removing that final item leaves exactly `x - c` calories. If the remaining food were not an optimal solution for `x - c`, we could replace it with a better one and obtain a solution for `x` using fewer items, contradicting optimality. Thus every optimal solution for `x` has the form `dp[x - c] + 1` for some available `c`. The algorithm examines every such `c` and takes the minimum, so `dp[x]` is optimal. Starting from the correct base case `dp[0] = 0` and processing states in increasing order establishes this property for every `x`, including `n`.

## Python Solution

```python
import sys
input = sys.stdin.readline

def solve(data=None):
    if data is None:
        data = sys.stdin.buffer.read().split()
    else:
        data = data.split()

    it = iter(data)
    n = int(next(it))
    k = int(next(it))
    calories = [int(next(it)) for _ in range(k)]

    # Food items larger than n can never appear in a valid solution.
    calories = [c for c in calories if c <= n]

    INF = n + 1
    dp = [INF] * (n + 1)
    dp[0] = 0

    for x in range(1, n + 1):
        best = INF
        for c in calories:
            if c > x:
                continue
            candidate = dp[x - c] + 1
            if candidate < best:
                best = candidate
        dp[x] = best

    return str(dp[n])

if __name__ == "__main__":
    sys.stdout.write(solve() + "\n")
```

The first part of the implementation reads the entire input with `sys.stdin.buffer.read()`. There is only one test case, so this keeps the parser simple while avoiding unnecessary overhead.

Food values greater than `n` are discarded. Such a food item cannot participate in an exact sum of `n` because every calorie value is positive. This filtering is not required for correctness, but it avoids useless comparisons in the inner loop.

`dp[0]` is initialized to zero because eating nothing produces zero calories. Every other state starts at `INF`, representing an unreachable amount. Using `n + 1` as infinity is sufficient because no solution can use more than `n` items when a one-calorie food exists, and any valid solution with fewer than or equal to `n` items is smaller than this sentinel.

The outer loop increases `x` from 1 to `n`. For each `x`, the inner loop tries every food value that can fit into the current total. The expression `dp[x - c] + 1` corresponds exactly to taking an optimal solution for the smaller total and appending one food item of `c` calories.

The order of the loops is deliberate. We process the total being formed, rather than processing each food type and then iterating over totals in a way that could accidentally impose a 0/1 restriction. Here every state may use a previously computed state involving the same food type, so unlimited repetition is naturally supported.

Python integers do not overflow, so no special numeric type is necessary. The main boundary condition is `c <= x`; without it, `x - c` would become negative and access the wrong DP state.

The problem statement does not specify an output for an unreachable target. The implementation consequently follows the intended problem assumption that an exact solution exists. If unreachable targets were allowed, an explicit convention from the statement would be needed before deciding how to print them.

## Complexity Analysis

| Measure | Complexity | Explanation |
| --- | --- | --- |
| Time | O(nk) | There are `n` calorie states, and each examines at most `k` food values. |
| Space | O(n) | The DP array stores one value for every total from 0 through `n`. |

The algorithm uses a single array rather than a two-dimensional table, because the answer for a total depends only on smaller totals. This keeps memory linear in the target calorie count and is appropriate for the one-second, 256 MB environment when `n` is within the intended DP range.

## Edge Cases

The first non-obvious case is the greedy failure

```
600
3
500
300
1
```

The DP begins with `dp[0] = 0`. When it reaches 300, it discovers `dp[300] = 1` using one 300-calorie item. At 600, the 300-calorie transition becomes `dp[300] + 1 = 2`. The 500-calorie transition requires `dp[100] + 1 = 101`, because the best way to make 100 calories is one hundred one-calorie items. The final answer is consequently 2.

The second case is an exact match:

```
12
2
6
4
```

When `x = 6`, the transition from `dp[0]` gives `dp[6] = 1`. At `x = 12`, using the 6-calorie food gives `dp[6] + 1 = 2`. The 4-calorie transition gives `dp[8] + 1 = 3`, so `dp[12]` becomes 2. The equality condition `c <= x` is what allows the exact 6-to-12 transition.

The third case demonstrates unlimited reuse:

```
9
2
3
5
```

The first reachable multiples of 3 are `dp[3] = 1`, `dp[6] = 2`, and `dp[9] = 3`. The algorithm is allowed to use the 3-calorie item again because `dp[9]` reads the already computed `dp[6]`. Treating the food types as one-use items would lose this solution.

The final boundary case is the smallest possible target:

```
1
1
1
```

Here `dp[0] = 0`, and the only transition is `dp[1] = dp[0] + 1 = 1`. The answer is exactly one food item. This also confirms that the array needs indices through `n`, inclusive, and that its size must be `n + 1`.
