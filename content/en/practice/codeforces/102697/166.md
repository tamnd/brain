## Solution
## Problem Understanding

The task has exactly three food choices: a steak contributes 500 calories, an apple contributes 100 calories, and a bread contributes 50 calories. Given a target `n`, which is guaranteed to be divisible by 50, we need to consume exactly `n` calories while using as few individual food items as possible. The output asks for the number of steaks, apples, and breads in that minimum-item solution, in that order.

The key restriction is that every calorie value is a multiple of 50. Dividing the entire problem by 50 turns the three food values into `10`, `2`, and `1`. That makes the structure especially simple: a steak replaces five apples or ten breads, so whenever a steak can be used without making the remaining calories impossible to form, using it can only reduce the number of food items.

The statement does not give an explicit upper bound for `n` on the problem page, so an algorithm should avoid work proportional to `n`, especially nested enumeration. A constant-time arithmetic solution is preferable and easily fits the one-second time limit and 256 MB memory limit.

The first edge case is exactly one bread. For input `50`, the only possible solution is `0` steaks, `0` apples, and `1` bread, so the output is `Steak: 0`, `Apples: 0`, `Bread: 1`. An implementation that assumes at least one steak or apple can be used would fail here.

The second edge case is a target that is not large enough for a steak but is exactly divisible by an apple. For input `200`, the correct output is `Steak: 0`, `Apples: 2`, `Bread: 0`. A careless implementation that always tries to reserve a steak first would be unable to use one, but the correct approach simply takes zero steaks and handles the remainder with apples.

A third useful boundary case is a target just above a steak. For input `550`, the correct output is `Steak: 1`, `Apples: 0`, `Bread: 1`. After taking the steak, the remaining 50 calories must become one bread. Forgetting the final remainder would produce an incomplete solution.

Finally, for an exact multiple of 500 such as `2500`, the answer is `5` steaks and zero of everything else. The output format requires all three counts, including zero counts, rather than omitting unused foods. The official examples demonstrate this behavior for `2500`.

## Approaches

A direct brute-force solution could try every possible number of steaks, then every possible number of apples, and check whether the remaining calories can be supplied by bread. For each pair of counts, the total calories are determined, so this method is correct because it eventually examines every possible combination. If `n` is large, however, the number of candidate pairs grows quadratically. After scaling calories by 50, the number of possible steak counts is about `n / 500`, and for each steak count there can be about `n / 100` apple counts, giving roughly `n² / 50000` combinations in the worst case. The exact constant is small, but the quadratic dependence is unnecessary.

The brute-force works because it explicitly searches the entire feasible space, but the structure of the denominations gives us something much stronger. A steak contains five times as many calories as an apple and ten times as many as bread. Since every target is divisible by 50, after choosing as many steaks as possible, the remaining amount is always a multiple of 50 and therefore can always be represented using apples and bread. Among those two foods, an apple contains twice as many calories as bread, so we should then use as many apples as possible. The remaining amount is either zero or exactly 50, which requires bread.

This gives a greedy solution with only integer division and remainders. We take `n // 500` steaks, remove their calories, take the maximum possible number of apples from the remainder, and use the final 50-calorie remainder as bread.

| Approach | Time Complexity | Space Complexity | Verdict |
| --- | --- | --- | --- |
| Brute Force | O(n²) | O(1) | Too slow for large n |
| Optimal Greedy | O(1) | O(1) | Accepted |

## Algorithm Walkthrough

1. Read the target number of calories `n`. Since `n` is divisible by 50, every remainder produced by removing 500-calorie steaks will also be divisible by 50.
2. Compute `steaks = n // 500`. This is the largest possible number of steaks. Using fewer steaks would replace at least one 500-calorie item with several smaller items, so it can never improve the minimum item count.
3. Subtract the calories of those steaks from `n`. The remaining calories are now strictly less than 500.
4. Compute `apples = remainder // 100`. This is the largest possible number of apples that fits into the remaining calories. Since apples are the second-largest food after steak, replacing an apple with bread can only increase the number of items.
5. Subtract the apple calories from the remainder. Because the remainder was a multiple of 50 and is now less than 100, the only possible value left is either 0 or 50.
6. Compute `bread = remainder // 50`. This produces either zero or one bread, exactly covering the remaining calories.
7. Print the three counts using the required labels.

### Why it works

The invariant is that after each greedy choice, the remaining calories are still exactly representable by the smaller food sizes. Taking the maximum possible number of steaks is safe because every steak has the largest calorie value, so replacing one steak with smaller foods requires at least two additional items. Once the steak count is fixed, the same argument applies to apples versus bread. Since the final remainder is guaranteed to be either zero or 50, bread completes the exact target. Thus the greedy construction is feasible, and every decision maximizes the use of the largest available food, which minimizes the total number of items.

## Python Solution

```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())

    steaks = n // 500
    n %= 500

    apples = n // 100
    n %= 100

    bread = n // 50

    print(f"Steak: {steaks}")
    print(f"Apples: {apples}")
    print(f"Bread: {bread}")

if __name__ == "__main__":
    solve()
```

The first division computes the maximum possible number of steaks. Using integer division rather than a loop makes this operation constant time.

The remainder operator immediately removes the calories accounted for by the steaks. At this point the remaining value is below 500. The same pattern is then applied to apples, leaving a value below 100.

Because the original target is divisible by 50, the final remainder must also be divisible by 50. Since it is below 100, it can only be 0 or 50, so integer division by 50 gives exactly the required bread count.

There is no floating-point arithmetic anywhere in the solution. This avoids rounding issues and also makes the divisibility argument exact. Python integers have arbitrary precision, so there is no integer overflow concern even if the target is larger than the usual 32-bit range.

The order of operations matters. We must remove steaks first, then apples, because the greedy proof depends on processing foods from largest calorie value to smallest.

## Edge Cases

For `50`, the algorithm first computes `50 // 500 = 0`, so no steak is selected. The remainder stays 50, and `50 // 100 = 0`, so no apple is selected either. Finally, `50 // 50 = 1`, producing `Steak: 0`, `Apples: 0`, `Bread: 1`. This confirms that the smallest legal target is handled without special cases.

For `200`, the steak count is `200 // 500 = 0`. The remaining 200 calories produce `200 // 100 = 2` apples, leaving zero calories. The final bread count is zero, giving `Steak: 0`, `Apples: 2`, `Bread: 0`. The algorithm never needs to force the largest food to appear.

For `550`, the steak count is `550 // 500 = 1`, leaving 50. No apple fits into 50, so the apple count is zero. The remaining 50 becomes exactly one bread. The result is `Steak: 1`, `Apples: 0`, `Bread: 1`, with two total food items.

For `2500`, the first division gives `2500 // 500 = 5` and the remainder becomes zero. Both subsequent divisions also produce zero. The output is `Steak: 5`, `Apples: 0`, `Bread: 0`, which confirms that zero-valued categories must still be printed and that an exact multiple of the largest denomination needs no smaller foods.

For a very large target such as `1000000000`, the algorithm performs the same three division stages as it does for a small input. It obtains two million steaks and zero remainder. No loop grows with the target, which is the main advantage of the arithmetic greedy solution.
