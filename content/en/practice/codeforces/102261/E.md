## Solution
## Problem Understanding

Нужно проанализировать небольшую программу на языке EX и для каждой объявленной функции определить, какие типы исключений могут выйти наружу из этой функции. Исключение считается возможным, если существует хотя бы один путь выполнения, на котором оно возникает и не подавляется окружающими `try ... suppress`.

У программы есть четыре вида конструкций. `maybethrow E` создаёт возможность выбросить исключение `E`. Вызов функции передаёт наружу любое исключение, которое может выйти из вызываемой функции. Блок `try { ... } suppress E1, E2, ...` удаляет перечисленные исключения из результата своего тела. Объявления функций находятся только на верхнем уровне, но функции могут вызывать друг друга в любом порядке и могут вызывать самих себя.

Для каждой функции нужно вывести её имя, количество различных исключений, которые могут выйти из неё, и сами исключения в лексикографическом порядке. Если различных исключений больше `x`, достаточно вывести только `x` первых.

Ограничение на `x` и число различных типов исключений равно `1000`, а число вызовов функций также не превосходит `1000`. Размер исходного текста может достигать миллиона символов. Это подсказывает разделить задачу на синтаксический разбор, линейный по размеру текста, и графовый анализ, зависящий в основном от числа функций, исключений и вызовов. Перебирать все возможные цепочки вызовов или многократно пересчитывать полные множества исключений нельзя, поскольку циклы в графе вызовов могут заставить такой алгоритм делать очень много повторной работы.

Первый неприятный случай связан с подавлением внутри вызываемой функции. Например:

```
1
2
func f() {
    try {
        maybethrow E
    } suppress E
}
func g() {
    f()
}
```

Для `f` ответ пустой, и для `g` тоже пустой. Исключение существует внутри тела `f`, но оно не выходит из `try`. Наивный подход, который просто добавляет все `maybethrow` в функцию, ошибочно припишет `E` обеим функциям.

Второй случай связан с подавлением именно в вызывающей функции:

```
1
2
func f() {
    maybethrow E
}
func g() {
    try {
        f()
    } suppress E
}
```

У `f` есть `E`, а у `g` его нет. Нельзя хранить только обычное ребро `g -> f`, потому что одно и то же вызываемое исключение может распространяться через один вызов и подавляться через другой.

Третий случай возникает при вложенных обработчиках:

```
1
1
func f() {
    try {
        try {
            maybethrow E
        } suppress X
    } suppress E
}
```

`E` подавляется внешним блоком, несмотря на то что внутренний блок подавляет только `X`. Для конкретного места вызова нужно учитывать все окружающие `try`.

Наконец, вызовы могут образовывать цикл:

```
1
2
func f() {
    g()
}
func g() {
    f()
}
```

Здесь ни одна функция ничего сама не выбрасывает, поэтому ответ для обеих функций пуст. Сам факт наличия цикла не создаёт исключение из ничего. Анализ должен находить только исключения, имеющие реальный источник.

## Approaches

Самый прямолинейный вариант состоит в том, чтобы хранить для каждой функции множество известных исключений и многократно просматривать все вызовы. Если вызываемая функция уже умеет выбрасывать `E`, то добавляем `E` вызывающей функции, если конкретный вызов не находится под подавляющим `try`.

Такой подход корректен, потому что множество возможных исключений монотонно растёт. В начале известны только исключения из `maybethrow`, после этого информация распространяется по вызовам, а процесс заканчивается, когда больше ничего добавить нельзя.

Проблема в количестве повторных проходов. При каждом проходе можно обнаружить только одну новую пару вида "функция может выбросить исключение". Таких пар не больше `V * K`, где `V` это число функций, а `K` число типов исключений. При каждом проходе приходится просматривать до `E` вызовов. Даже при ограничениях порядка `1000` это даёт до `10^9` проверок.

Здесь помогает другая точка зрения. Зафиксируем один конкретный тип исключения `E`. Теперь нам не нужно вычислять множества всех исключений одновременно. Нужно только ответить на вопрос, из каких функций может выйти именно `E`.

Для этого строим граф вызовов в обратном направлении. Если функция `f` вызывает `g`, то после нахождения `E` в `g` мы можем попробовать добавить `E` в `f`. Единственное дополнительное условие состоит в том, что конкретный вызов не должен находиться под обработчиком, подавляющим `E`.

Получается обычный обход графа. Начальные вершины это функции, в которых `E` действительно может возникнуть и не подавляется непосредственно в месте возникновения. Затем BFS идёт от вызываемых функций к их вызывающим функциям. Каждое обратное ребро разрешено только тогда, когда окружающий вызов не подавляет `E`.

Эта идея также соответствует опубликованному разбору задачи, где предлагается строить граф вызовов и независимо распространять каждое исключение обходом графа.

После обработки всех типов исключений достаточно проходить их в лексикографическом порядке. Когда очередная функция получает исключение, добавляем его в ответ только если там ещё меньше `x` элементов. Поскольку исключения рассматриваются от меньшего к большему, первые `x` добавленных значений автоматически являются требуемыми.

| Approach | Time Complexity | Space Complexity | Verdict |
| --- | --- | --- | --- |
| Brute Force | `O(K * V * E)` | `O(V * K + E)` | Too slow |
| Optimal | `O(S + K * E + P)` | `O(S + V + E + P)` | Accepted |

Здесь `S` обозначает размер исходного текста, `K` число типов исключений, `E` число вызовов, а `P` число реально найденных пар "функция может выбросить исключение". В худшем случае `P` ограничено количеством источников и распространений, а при `E <= 1000` графовая часть остаётся небольшой.

## Algorithm Walkthrough

1. Сначала разбираем исходный текст и создаём вершину для каждой функции. Поскольку вызов может идти до объявления функции, при встрече вызова сохраняем имя вызываемой функции, а связываем его с вершиной только после разбора всех объявлений.
2. Для каждого блока `try` создаём отдельный контекст. Контекст хранит родительский контекст, список исключений, подавляемых непосредственно этим `try`, и множество исключений, которые возникают непосредственно в его теле.

Для вызова также запоминаем контекст, в котором этот вызов находится. Это позволяет отложить обработку `suppress` до завершения синтаксического разбора.
3. Представляем множество типов исключений внутри контекста одним целым числом. Если типу исключения соответствует бит `i`, то установленный `i`-й бит означает, что этот тип подавляется.

Это особенно удобно для вложенных `try`. Эффективная маска контекста равна `effective[parent] | suppress[current]`. Значит, в ней содержатся все исключения, подавляемые любым обработчиком от текущего места до границы функции.
4. После завершения разбора вычисляем эффективную маску каждого контекста. Контексты создаются от внешних к внутренним, поэтому родитель уже обработан к моменту вычисления ребёнка.
5. Для каждого непосредственного `maybethrow` проверяем эффективную маску его контекста. Если бит исключения отсутствует, это исключение действительно может выйти из функции, в которой находится данный оператор. Добавляем его в начальные вершины соответствующего исключения.

Если бит установлен, исключение полностью подавлено ещё до выхода из текущего контекста и не должно становиться источником распространения.
6. Для каждого вызова после разбора разрешаем имя вызываемой функции и добавляем обратное ребро от вызываемой функции к функции, содержащей вызов. Вместе с ребром сохраняем эффективную маску контекста вызова.

Для фиксированного исключения `E` ребро можно использовать тогда и только тогда, когда бит `E` отсутствует в этой маске.
7. Сортируем все найденные имена исключений лексикографически. Обрабатываем их по одному, начиная с самого маленького.
8. Для очередного исключения запускаем BFS от всех функций, где это исключение может возникнуть непосредственно. Каждая посещённая функция может выбросить рассматриваемое исключение.
9. Из посещённой функции рассматриваем все обратные рёбра. Если конкретный вызов не подавляет рассматриваемое исключение, добавляем функцию, содержащую этот вызов, в очередь.
10. Когда функция впервые становится посещённой для текущего исключения, добавляем исключение в её ответ, если там ещё меньше `x` элементов. Повторные посещения для этого же исключения не нужны.
11. Если у всех функций уже набрано по `x` ответов, оставшиеся типы исключений можно не обрабатывать. Если хотя бы у одной функции меньше `x` ответов, продолжаем до конца списка исключений.
12. Для каждой функции печатаем её имя, затем количество сохранённых исключений, затем сами имена в найденном порядке. Если исключений нет, печатаются имя функции и `0`.

### Why it works

Рассмотрим фиксированное исключение `E`. Инвариант BFS состоит в том, что после завершения обхода функция посещена тогда и только тогда, когда существует цепочка реальных источников `E` и вызовов, по которой `E` доходит до этой функции, не попадая на вызов, подавляющий `E`.

Все начальные вершины являются настоящими источниками `E`, потому что исключение возникает через `maybethrow` и не подавляется его контекстом. При переходе по обратному ребру мы проверяем именно тот контекст, в котором находится вызов. Поэтому исключение добавляется к вызывающей функции только в случае, когда оно действительно может пройти через этот вызов. Обратное направление обхода позволяет пройти любую конечную цепочку вызовов, а циклы безопасно обрабатываются массивом посещённых вершин.

Значит, после BFS множество посещённых функций точно совпадает с множеством функций, из которых может выйти `E`. Поскольку все типы исключений обрабатываются в лексикографическом порядке, первые `x` исключений, попавшие в ответ каждой функции, являются `x` лексикографически наименьшими.

## Python Solution

```python
import sys
import re
from collections import deque

input = sys.stdin.readline

TOKEN_RE = re.compile(r"[A-Za-z0-9_]+|[{}(),]")

def solve():
    x = int(input())
    n = int(input())

    source = sys.stdin.buffer.read().decode()
    tokens = TOKEN_RE.findall(source)
    m = len(tokens)
    pos = 0

    func_id = {}
    func_names = []

    # Context data.
    # Every function gets one root context.
    parent = []
    owner = []
    suppress = []
    direct_throws = []

    # Each call is (caller_function, callee_name, context_id).
    calls = []

    # Exception name -> bit index.
    exc_id = {}
    exc_names = []

    def get_exc_id(name):
        eid = exc_id.get(name)
        if eid is None:
            eid = len(exc_names)
            exc_id[name] = eid
            exc_names.append(name)
        return eid

    for _ in range(n):
        if tokens[pos] != "func":
            raise ValueError("invalid program")

        name = tokens[pos + 1]
        pos += 2

        # ()
        if tokens[pos] != "(":
            raise ValueError("invalid function header")
        pos += 1
        if tokens[pos] != ")":
            raise ValueError("invalid function header")
        pos += 1

        if tokens[pos] != "{":
            raise ValueError("invalid function body")
        pos += 1

        fid = len(func_names)
        func_id[name] = fid
        func_names.append(name)

        root = len(parent)
        parent.append(-1)
        owner.append(fid)
        suppress.append(0)
        direct_throws.append(0)

        # Stack contains contexts whose blocks are currently open.
        # The root context represents the function body.
        block_stack = [root]

        while block_stack:
            tok = tokens[pos]

            if tok == "}":
                pos += 1
                ctx = block_stack.pop()

                if parent[ctx] != -1:
                    # The closing brace belongs to a try block.
                    if tokens[pos] != "suppress":
                        raise ValueError("missing suppress")

                    pos += 1
                    mask = 0

                    while True:
                        exc_name = tokens[pos]
                        pos += 1
                        mask |= 1 << get_exc_id(exc_name)

                        if tokens[pos] != ",":
                            break
                        pos += 1

                    suppress[ctx] = mask

                continue

            if tok == "try":
                pos += 1
                if tokens[pos] != "{":
                    raise ValueError("invalid try")
                pos += 1

                new_ctx = len(parent)
                parent.append(block_stack[-1])
                owner.append(fid)
                suppress.append(0)
                direct_throws.append(0)

                block_stack.append(new_ctx)
                continue

            if tok == "maybethrow":
                pos += 1
                exc_name = tokens[pos]
                pos += 1

                eid = get_exc_id(exc_name)
                direct_throws[block_stack[-1]] |= 1 << eid
                continue

            # The remaining statement form is a function call:
            # name ( )
            callee_name = tok
            pos += 1

            if tokens[pos] != "(":
                raise ValueError("invalid call")
            pos += 1

            if tokens[pos] != ")":
                raise ValueError("invalid call")
            pos += 1

            calls.append((fid, callee_name, block_stack[-1]))

    # Compute all effective suppression masks.
    # Parents are always created before children.
    effective = [0] * len(parent)

    for ctx in range(len(parent)):
        p = parent[ctx]
        if p == -1:
            effective[ctx] = suppress[ctx]
        else:
            effective[ctx] = effective[p] | suppress[ctx]

    # For every exception, keep the functions where it can originate
    # without already being suppressed.
    seed_by_exc = [[] for _ in exc_names]

    for ctx in range(len(parent)):
        possible = direct_throws[ctx] & ~effective[ctx]
        while possible:
            bit = possible & -possible
            eid = bit.bit_length() - 1
            seed_by_exc[eid].append(owner[ctx])
            possible -= bit

    # Reverse call graph:
    # rev[g] contains calls f -> g as (f, suppression_mask).
    rev = [[] for _ in func_names]

    for caller, callee_name, ctx in calls:
        callee = func_id[callee_name]
        rev[callee].append((caller, effective[ctx]))

    order = sorted(range(len(exc_names)), key=exc_names.__getitem__)

    answers = [[] for _ in func_names]
    seen = [0] * len(func_names)
    stamp = 0

    remaining = len(func_names)

    for eid in order:
        if remaining == 0:
            break

        seeds = seed_by_exc[eid]
        if not seeds:
            continue

        stamp += 1
        bit = 1 << eid

        q = deque()

        for f in seeds:
            if seen[f] != stamp:
                seen[f] = stamp
                q.append(f)

        while q:
            g = q.popleft()

            if len(answers[g]) < x:
                answers[g].append(exc_names[eid])
                if len(answers[g]) == x:
                    remaining -= 1

            for caller, blocked in rev[g]:
                if blocked & bit:
                    continue
                if seen[caller] == stamp:
                    continue

                seen[caller] = stamp
                q.append(caller)

    out = []

    for name, ans in zip(func_names, answers):
        out.append(name + ":")
        out.append(str(len(ans)))
        out.extend(ans)

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```

Парсер использует регулярное выражение только для выделения идентификаторов и нескольких знаков пунктуации. Пробелы и переводы строк после этого вообще не имеют значения, поэтому программа одинаково работает с компактным и сильно разреженным форматированием исходника.

Для каждого `try` создаётся контекст с указателем на родителя. Сам список `suppress` появляется только после закрывающей `}`, но это не мешает разбору, поскольку операции внутри блока уже ссылаются на созданный контекст. После получения списка подавляемых исключений маска контекста просто заполняется.

Использование целого числа как множества исключений существенно упрощает работу с вложенными блоками. Операция `effective[parent] | suppress[ctx]` сразу объединяет все окружающие обработчики. Проверка одного исключения выполняется одной операцией `blocked & bit`.

Для `maybethrow` сохраняется не отдельная запись на каждое повторение, а битовая маска исключений, которые непосредственно возникают в данном контексте. Это уменьшает объём памяти, особенно если один и тот же тип исключения выбрасывается много раз.

После разбора имена функций вызовов разрешаются через `func_id`. Обратный граф нужен потому, что BFS начинается с функций-источников. Если `g` может выбросить `E`, то нас интересуют функции, которые вызывают `g`, а не функции, которых вызывает `g`.

Массив `seen` не очищается после каждого BFS. Вместо этого используется возрастающий `stamp`. Для нового исключения достаточно увеличить `stamp`, после чего старые значения автоматически считаются неактуальными. Это избавляет от лишнего прохода по всем функциям перед каждым обходом.

Особенность остановки после `x` ответов состоит в том, что обход для самого исключения всё равно продолжается. Одна функция может уже иметь `x` результатов, а другая ещё только получить текущий тип. Исключение нужно распространить полностью, иначе можно случайно пропустить его для другой функции.

Целочисленное переполнение здесь невозможно: Python поддерживает целые числа произвольной длины, а битовая маска содержит всего до `1000` значащих битов.

## Worked Examples

### Sample 1

Восстановим из приведенного в условии фрагмента полный ввод с `x = 1` и двумя функциями:

```
1
2
func func1() {
maybethrow exc1
try {
maybethrow exc2
maybethrow exc3
} suppress exc1, exc2, exc3
maybethrow exc4
}
func main() {
try {
func1()
} suppress exc1
}
```

Для `func1` исключения `exc2` и `exc3` появляются внутри блока, который их подавляет. `exc1` появляется вне него, а `exc4` тоже выходит напрямую.

| Step | Current function | Current exception | Action | Result |
| --- | --- | --- | --- | --- |
| 1 | `func1` | `exc1` | direct throw, not suppressed | seed `func1` |
| 2 | `func1` | `exc2` | direct throw, suppressed | ignored |
| 3 | `func1` | `exc3` | direct throw, suppressed | ignored |
| 4 | `func1` | `exc4` | direct throw, not suppressed | seed `func1` |
| 5 | `main` | `exc1` | call to `func1`, `exc1` suppressed | blocked |
| 6 | `main` | `exc4` | call to `func1`, `exc4` not suppressed | visit `main` |

Поскольку `x = 1`, `func1` получает только `exc1`, а `main` получает `exc4`.

Ожидаемый вывод:

```
func1:
1
exc1
main:
1
exc4
```

Этот пример проверяет сразу два разных уровня подавления. `exc1` существует в `func1`, но подавляется уже при вызове из `main`, тогда как `exc4` проходит через тот же вызов.

### Custom Example 2

Рассмотрим вложенный вызов:

```
1
3
func a() {
b()
}
func b() {
try {
maybethrow z
} suppress z
maybethrow a
}
func c() {
a()
}
```

| Step | Function | Exception | State |
| --- | --- | --- | --- |
| 1 | `b` | `z` | suppressed inside `try`, no seed |
| 2 | `b` | `a` | unsuppressed seed |
| 3 | `a` | `a` | reverse edge `a -> b`, visit `a` |
| 4 | `c` | `a` | reverse edge `c -> a`, visit `c` |

Итоговые ответы:

```
a:
1
a
b:
1
a
c:
1
a
```

Здесь BFS показывает, как одно исключение распространяется сразу через несколько уровней вызовов.

### Custom Example 3

Теперь цикл без источника исключения:

```
1
2
func f() {
g()
}
func g() {
f()
}
```

| Step | Function | Seeds | BFS result |
| --- | --- | --- | --- |
| `f` | none | empty | empty |
| `g` | none | empty | empty |

Ни одна вершина не становится начальной. Поэтому BFS вообще не запускается для какого-либо исключения, и цикл ничего не создаёт.

Ожидаемый вывод:

```
f:
0
g:
0
```

Этот случай показывает, почему нельзя считать сам факт рекурсивного вызова источником исключения.

## Complexity Analysis

| Measure | Complexity | Explanation |
| --- | --- | --- |
| Time | `O(S + P + K * E)` | `S` символов разбираются один раз, каждое найденное исключение распространяется по обратным рёбрам |
| Space | `O(S + V + E + P)` | хранятся контексты, функции, вызовы, обратный граф и ответы |

Здесь `S` это размер программы, `V` число функций, `E` число вызовов, `K` число типов исключений, а `P` число различных пар "функция может породить непосредственное исключение". При `K <= 1000` и `E <= 1000` графовая часть требует порядка нескольких миллионов проверок. Разбор исходного текста линейный, поэтому ограничение в миллион символов также укладывается в разумные пределы.

Отдельно стоит учитывать стоимость операций над Python `int`. Маски содержат не более `1000` битов, поэтому объединение масок работает с очень небольшим числом машинных слов. На заданных ограничениях это существенно дешевле хранения и объединения обычных множеств Python.

## Edge Cases

### Exception suppressed where it is created

Для входа

```
1
1
func f() {
try {
maybethrow E
} suppress E
}
```

создаётся контекст `try` с маской `E`. У `maybethrow E` эффективная маска также содержит `E`, поэтому выражение `direct_throws & ~effective` удаляет этот бит. Начальных вершин для `E` нет, BFS не запускается, и результат равен:

```
f:
0
```

Алгоритм не путает "исключение когда-то было выброшено" с "исключение действительно вышло из функции".

### Исключение подавляется только в вызывающей функции

Для

```
1
2
func f() {
maybethrow E
}
func g() {
try {
f()
} suppress E
}
```

`f` получает `E` как непосредственный источник. Для вызова `g -> f` эффективная маска содержит `E`. Когда BFS от `f` смотрит обратное ребро, проверка `blocked & bit` оказывается истинной, поэтому `g` не посещается.

Получаем:

```
f:
1
E
g:
0
```

Это показывает, почему фильтр должен храниться вместе с конкретным ребром, а не вместе с вызываемой функцией.

### Вложенные обработчики

Для

```
1
1
func f() {
try {
try {
maybethrow E
} suppress X
} suppress E
}
```

внутренний контекст получает `X`, а внешний контекст получает `E`. Эффективная маска внутреннего контекста равна `X | E`. Бит `E` присутствует в ней, поэтому источник исключения не становится seed.

Результат:

```
f:
0
```

Объединение масок по цепочке родителей корректно обрабатывает любое количество вложенных `try`.

### Рекурсия без источника

Для

```
1
2
func f() {
g()
}
func g() {
f()
}
```

ни один контекст не содержит `maybethrow`, поэтому для каждого исключения список seed пуст. Цикл не создаёт новые вершины самостоятельно.

Результат:

```
f:
0
g:
0
```

Это соответствует смыслу "может быть выброшено": должна существовать реальная инструкция, способная породить исключение.

### Рекурсия с источником

Для

```
1
2
func f() {
g()
}
func g() {
f()
maybethrow E
}
```

`g` становится seed для `E`. BFS идёт по обратному ребру `g -> f`, посещает `f`, затем рассматривает обратное ребро `f -> g`, но `g` уже посещена для текущего BFS.

Обе функции получают:

```
f:
1
E
g:
1
E
```

Массив `seen` гарантирует, что цикл не приводит к бесконечному обходу.

### Больше `x` исключений

Если

```
2
1
func f() {
maybethrow C
maybethrow A
maybethrow B
}
```

то все три типа действительно выходят из `f`, но сортировка даёт `A`, `B`, `C`. При `x = 2` результат:

```
f:
2
A
B
```

Обработка исключений в лексикографическом порядке позволяет не выполнять дополнительную сортировку ответа и одновременно гарантирует правильный выбор первых `x` типов.

### Нет подавления, но несколько разных вызовов

Если функция вызывает одну функцию под `suppress A`, а другую без обработчика, нельзя хранить единую маску для вызывающей функции. Каждое ребро получает маску своего собственного контекста. Именно поэтому два вызова одной и той же функции могут распространять разные подмножества исключений.

### Повторное возникновение одного исключения

Если `maybethrow E` встречается сто раз в одной функции, результат всё равно содержит только одно `E`. Битовая маска автоматически убирает дубликаты ещё во время разбора, поэтому размер данных не зависит от количества повторений одного типа исключения.

### Функция объявлена после вызова

При разборе вызова имя сохраняется как строка, а разрешение происходит после того, как прочитаны все объявления функций. Поэтому программа вида

```
1
2
func a() {
b()
}
func b() {
maybethrow E
}
```

обрабатывается так же, как если бы `b` была объявлена первой. После построения `func_id` имя `b` успешно превращается в идентификатор вершины графа.
